# v0.4.0

Minor: the world becomes editable. A block placed and a block broken, written
down, and still there when the page is opened again.

Everything before this release is a pure function of the seed. This one adds the
first thing that is not: a record of what a player did, held beside the terrain
and laid over it every time a chunk is built.

**Storage is the browser's own database and nothing else.** There is no server
here, local or hosted, and standing one up would be the larger half of the work
for a release whose point is the edit path. What that costs is stated rather
than hidden: a browser can clear its own storage, so a world lives as long as
the browser lets it. [`ARCHITECTURE.md`](../ARCHITECTURE.md) puts the local
server in 0.5.0 and the hosted one in 1.0.0, and both read the same records.

**The engine is also the authoring tool, and that is temporary.** A knob that
moves the ground moves it under whatever a player already built. Later the two
separate and a world opens from a parameter set that never changes again; until
then, changing a world's shape is understood to walk away from its edits, and
I-5 is about making sure it walks away rather than corrupting anything.

---

## Done when

- A crosshair says where the ray leaves from, and a wireframe hexagon
  outlines the cell a block would be placed in.
- Clicking places a block against the face being aimed at. The type is picked at
  random.
- Clicking the other button removes the hexagon being aimed at.
- Reloading the page rebuilds the planet from the seed and both changes are
  still there.
- A built structure is still visible when the chunk holding it is drawn coarse.
- The deepest layer of the crust cannot be broken.

## What is already decided, and is not being decided again

[Doc 27](../docs/27-block-state.md) owns block state and settles most of the
shape of a record before this release opens.

| Decided | Where |
|---|---|
| A block state is 12 bits of type and 4 of rotation, 16 in total | [doc 03](../docs/03-addressing.md), [doc 27](../docs/27-block-state.md) |
| A record on disk is `[address 29][layer 11][state 16]` = 56 of 64 bits | [doc 27](../docs/27-block-state.md) |
| The planet is not in the record — the store already belongs to one | [doc 27](../docs/27-block-state.md) |
| A block type number is a position in a list, never a hash of its name | [doc 27](../docs/27-block-state.md) |
| An explicit *air* entry is meaningful: never touched and mined out differ | invariant 6 |
| Anything larger than 16 bits goes in a side table: tag, length, payload | [doc 27](../docs/27-block-state.md) |
| Writing a block clears that cell's side data | [doc 27](../docs/27-block-state.md) |
| The twelve pentagon columns refuse placement and removal at every layer | invariant 15 |
| An edit names a cell and a resulting block state, never an outcome | [doc 30](../docs/30-authority-and-cheating.md) |

The last two are requirements on the edit path rather than candidates. The
pentagon refusal is a comparison against `degree`, which `chamfer/addressing`
already answers; the edit shape is what keeps a validating server from being a
protocol change later.

### The two tiers, and which question each one answers

The store has two halves and they are sized for opposite things. Naming them
apart is what lets the delta list stay small while the world stays extensible.

**The delta list is fixed-width and holds every ordinary block.** One record per
edited cell: where, and the 16 bits saying what is there now. No allocation, no
variable length, nothing to walk. This is what the mesher reads, what travels to
a worker, and what a click writes.

**The side table is variable-width and holds almost nothing.** Cell ID to a run
of `(tag, length, payload)` entries. A chest's inventory, a sign's text, an
owner, a name — anything a future feature invents gets a tag of its own. The
length is what makes it survivable: a build meeting a tag it has never heard of
reads the length and steps over it, so an older build can open a newer store
instead of giving up on the file.

**Almost every cell has no side-table row at all**, which is why the expansion
room costs the delta list nothing. Doc 27 measured the shapes that instead put
a marker on every cell — a flag bit in the block state, or a per-chunk bitmap —
and both spend resident storage on a question nothing on the frame path asks.
The one rule joining the two halves is doc 27's: writing a block clears that
cell's side data, so a blob is never left behind by the block it belonged to.

## I-1 — What one change to the world is

**From:** the release goal
**Step:** 1

### The problem

Doc 27 fixed the record's fields and left the store's shape open. The store is a
row per chunk, which is what [`ARCHITECTURE.md`](../ARCHITECTURE.md) already
commits to for 1.0.0 — chunk ID to a blob of deltas, one `get` and one `put`.
That much is settled. What is open is how much of the address each record inside
a row still has to carry, because whatever the row's key already names, the
record is repeating.

**Chunk size is a knob on the panel today.** `chunkCells` runs from 8 to 64 and
sets the chunk level as `depth − log2(chunkCells)`. That matters here because a
chunk-relative record names a slot in a triangle of side `2 ^ (depth −
chunkLevel)`, so the slot's meaning moves when that slider does.

**And chunk size decides nothing about the world.** A chunk is where the address
is cut into a prefix and a local part; the terrain is `columnAt(face, i, j)` and
never sees the cut. Every block sits at exactly the same place at 8 cells a
chunk and at 64. So dragging that slider is a drawing decision, and it must not
be able to lose a build — which rules out any record that cannot be re-filed
under a new cut.

Three numbers set the frame. A cell word is `30 + 2 x depth` bits — 52 at the
shipped depth 11, 56 with the state — past the 53 a JavaScript `number` counts
exactly, so anything carrying the whole word is two 32-bit halves. A slot inside
a 64-cell chunk is one of 2,145, which is 12 bits. And the layer is 11.

### Candidates

**A — Every record carries the whole cell word.**

56 bits, stored as the two 32-bit halves `CellId` already uses: 8 bytes a
record. Every record says which cell it is with no help from anything around it,
so it can be re-filed under a new cut, put on a wire, or handed to a probe
unchanged.

What it costs: the chunk's own face and path are repeated in every record in the
row, which is the thing the key already said. And the mesher has to take a word
apart into a slot and a layer for every record on every build.

**B — Every record is relative to its row, and nothing says which cut.**

`[slot 12][layer 11][state 16]` is 39 bits. Split across a `Uint32Array` for the
position and a `Uint16Array` for the state it is 6 bytes a record, and the
mesher uses the slot directly with nothing to decode.

What it costs is the whole store, the day somebody drags the Chunk slider. A
slot is a rank inside a triangle whose side the chunk level sets, so with no
record of which chunk level was in force the numbers cannot even be converted —
they are simply wrong, and wrong quietly.

**C — Records relative to their row, and the store says which cut it was
written under.**

The same 6-byte record as B, and the store carries a header: the subdivision
depth and the chunk level its slots were counted at. On a build
where the header matches the world, the records are used with no conversion at
all, which is the common case and the fast path. Where it does not match, every
record converts — `joinPath` turns a path and a slot into lattice coordinates
and `splitPath` cuts them again at the new level, both of which exist — and the
row is re-filed. Nothing is lost, because the header supplies exactly what B was
missing.

What it costs is one header and a conversion path that runs rarely.

### Where the header lives

The header is one per store, not one per row. Subdivision depth and chunk level
are properties of the world rather than of any chunk in it, so writing them into
every row would repeat the same two numbers a few thousand times over — the very
thing this item is about. One header, read once when the store is opened, says
what its slot numbers were counted against.

That also makes a re-cut a single decision instead of a lazy one. The header
either matches the world being opened or it does not; if it does not, the whole
store converts in one pass and is written back matching. A per-row header would
leave a store half in one cut and half in the other, with no moment where it was
known to be consistent.

The row itself is a **chunk**, not a face. A chunk is the unit that gets loaded
and meshed, so its records are wanted at exactly the moment it is built — one
read, at the one time it is needed. A face at the shipped depth is a twentieth
of a planet and millions of cells, which is a row nothing ever wants whole.
[`ARCHITECTURE.md`](../ARCHITECTURE.md) already commits to a chunk-keyed row for
the hosted store, so this is the same cut in both places.

### The shape that is not in dispute

Whatever the store holds, **a side-table key is a full cell ID**, because doc 27
keys it by one, and **an edit message names a cell**, because doc 30 requires it.
The store's own packing is a separate question from those two, and conflating
them is what makes A look forced. A batch of edits over a wire is a chunk key
followed by a run of records, which carries the same information either way;
which of the two forms travels is a later decision and not this release's.

### What a chunk-size change actually costs

Chunk size is not a data invalidator under A or C, and it is under B. Under all
three it is a **re-filing event**, because the row's key *is* the chunk and a
different cut means different rows. The difference is whether the records inside
can find their way to the new rows: under C the header says which plan the slot
numbers were counted against, so every record converts; under B there is nothing
to convert from and they are simply wrong.

## I-2 — Where a change is applied, so the mesh and the player agree

**From:** the release goal
**Step:** 1

### The problem

The world is built in two places that never speak to each other. A mesh worker
runs `generateChunk` and meshes it, and the blocks never come back across —
`MeshResult` carries geometry and nothing else, on purpose, because a chunk is
478 KB of blocks and 210 KB of geometry. Meanwhile the thread that draws holds
its own `TerrainGenerator` and asks `blockAtPosition` for collision and for
whether the player is swimming.

So a placed block that only the worker knows about is one the player walks
through, and one only the drawing thread knows about is one that is never drawn.

### Candidates

**A — The changes travel with the job.**

The thread that draws owns the store. A mesh job for a chunk carries that
chunk's records; the worker runs `generateChunk` and then writes them over it,
before meshing. An edit re-issues the job for that one chunk. The same thread
keeps the records in a map for `blockAtPosition`, so the player and the picture
read one source.

One rule and no cases: **a chunk is generated, then patched.** The blob is sent
again whenever the chunk changes level, which at tens of records is a few
hundred bytes against 210 KB of geometry coming the other way.

**B — Every worker holds the store.**

Workers open the database themselves and keep a resident map. An edit is
broadcast to all of them and to the drawing thread. Nothing rides on the job.

What it costs is coherence: as many copies as there are cores, all of which must
have the write before the re-mesh, so an edit becomes a round of messages with
an ordering requirement rather than one job with a payload.

## I-3 — Which hexagon the player is looking at

**From:** the release goal
**Step:** 1 — **chosen: A**, at the owner's instruction

### The problem

[Doc 09](../docs/09-ray-traversal.md) designs block picking as a grid walk and
nothing implements it. There is no ray in the engine at all: the client turns a
camera into a matrix and a frustum, and the only thing that ever asks where a
point sits is `positionToCell`.

Both breaking and placing need the same walk, and placing needs one thing more
than breaking does. Breaking wants the first solid cell along the look
direction. Placing wants the last empty cell before it, which is where the new
block goes — so aiming at the side of a wall puts the block beside it rather
than on top.

### Candidates

**A — Build doc 09's walk. Chosen.**

Step cell to cell: pick the neighbour the ray leaves through, cross a face edge
where it comes to one, step a layer where it crosses a layer boundary. Exact by
construction, and it names the face the ray crossed, so the placement cell falls
out of the walk rather than being inferred.

It is the largest piece of work in this release, and its edge cases are the ones
this project already knows are sharp: crossing between faces mid-walk, arriving
at a pentagon where the ring is five long, and interleaving the horizontal step
with the radial one. It has a second caller waiting for it — doc 25 requires a
swept segment rather than an endpoint for a falling player, since a
non-colliding block is one a fast mover passes through.

**B — March the ray in fixed steps.** Not taken.

Walk out from the eye a fraction of a block at a time, ask `positionToCell` at
each step, stop at the first solid cell. Both answers come out of one loop, and
a step that cuts a corner misses a cell the walk would have entered — which
shows up as picking the block behind the one you aimed at. It is a lookalike of
a walk this project has already designed.

## I-4 — The marker over the hexagon

**From:** the release goal
**Step:** 1 — **chosen: the placement cell, outlined, plus a crosshair**, at the
owner's instruction

### The problem

Aiming has to be visible before clicking is safe, and a hexagon on a sphere is
not where a square-grid reflex expects it. `cellCorners` already returns a
cell's six corners, and `MarkerRenderer` already draws a line list with a
position and a color per vertex, so the geometry and the pipeline both exist.

### What is built

**Two things, and they answer different questions.**

A **crosshair** at the centre of the screen says where the ray leaves from. It
is drawn whatever the ray finds, including nothing, so aiming at the sky still
shows where aiming happens. Without it there is no way to tell a miss from a
ray that found nothing.

An **outline of the cell a block would be placed in** — the air cell the ray was
last in before it met something solid, which is the cell the walk in I-3 already
produces. Plain lines, no fill and no shading: the top ring, the bottom ring and
the six verticals, so it reads as a cell rather than as a patch of ground, and
so it is visible against a wall as well as against a floor.

**The outline stands on the result of the click, not on what is under the
crosshair.** Aiming at the side of a wall puts the block beside the wall, and
the outline is where it will go rather than where the ray hit — which is the
answer to the question somebody about to click is actually asking. The cell
being broken is the neighbour of the one outlined, so the outline says which
block is under the crosshair as well, one step away.

## I-5 — Which world a set of changes belongs to

**From:** the release goal
**Step:** 1 — **chosen: B**, at the owner's instruction

### The problem

Doc 27 says the planet is not in the record because the file already belongs to
one planet. There is no file here. There is a browser database and a query
string full of knobs.

**In the shape this project is heading for, the knobs are read once.** A world is
created from a parameter set and the terrain never changes again; the editor and
the engine are separate programs and only the first one has sliders. What the
store needs then is a **world identity** — a value assigned at creation and
never recomputed — and the question of what happens when a knob moves does not
arise, because no knob moves.

Today the two programs are one, so the sliders are live and there is no creation
moment to assign an identity at. The identity has to be derived from something,
and the only thing available is the shape itself. **That derivation is a
stand-in for an assigned identity, not a design.** When the authoring tool
separates, the key becomes a value written once and this item's mechanism is
deleted rather than migrated.

What it has to achieve in the meantime is narrow: blocks placed in one world
must never appear in a differently-shaped one. Losing edits to a slider is
acceptable here — the storage is the browser's and the editing has no value
beyond seeing that it works — and showing somebody else's wall floating in a
terrain that no longer holds it up is not.

### Candidates

**B — The identity is derived from the world's shape. Chosen.**

Every knob that decides where a cell is or what block sits there is folded into
one key. A differently-shaped world is a different key and an empty store, and
setting the knobs back reaches the earlier store again, since the key is derived
rather than remembered.

Two things stay out of the key because neither moves a block: **chunk size**,
which decides how the address is cut for drawing, and every knob that only
decides how the world is drawn or how far it is drawn to. Dragging those keeps
the world they were dragged in.

**A — The identity is the seed and the planet's size.** Not taken.

Seed, subdivision depth, block size, crust depth only, letting terrain knobs move
the ground under existing blocks. It keeps one world across knob-twiddling, at
the cost of walls left standing in air that no longer has ground under it, which
is the one outcome this item exists to prevent.

## I-6 — Whether the store carries a block registry

**From:** [doc 27](../docs/27-block-state.md), and `BlockType.ts`'s own note
**Step:** 1

### The problem

`packages/engine/src/generation/terrain/BlockType.ts` carries seven numbered
types and a line saying doc 27's registry replaces the list once a save format
exists. This release is where one starts existing.

The registry is not a decision about which blocks the game has. It is a list of
names written beside the numbers, so that a stored `3` can be checked against
`chamfer:grass` rather than being trusted. Doc 27's rules are three: append
only, never reuse a slot, the store carries the names. A full 4,096-entry
registry is about 96 KB and this world has seven entries in it.

Its whole job is the day the list changes. I-8 adds an eighth type this release,
which is that day arriving during the release that would write the store.

### Candidates

**A — Write the registry now.** The store gets a header holding the names in
order, and loading compares it against the build's own list. A mismatch is a
refusal or a remap rather than a house quietly turning into dirt. Costs a header
field and one comparison at load, both small.

**B — Defer it, and record why.** Seven types, one build, no other machine, and
a store written this week read by the same build. The numbers are the enum's and
the enum is in the source. The header goes in when the type list first changes.

## I-7 — A change is invisible as soon as its chunk is drawn coarse

**From:** noticed while writing I-2
**Step:** 1

### The problem

A chunk is drawn at a level of detail chosen by distance. `WorldShape.atLod`
drops the subdivision depth by the level and divides the crust depth by two per
level, keeping the same chunk triangle and the same 561 slots — so a coarse
chunk covers the same ground with cells twice as wide and layers twice as tall
per level out.

Nothing carries an edit across that. A chunk built at level 2 runs the terrain
at a coarser depth and knows nothing of a record written against a fine cell, so
a built structure is complete up close and gone entirely a few hundred metres
back. Losing detail at distance is expected. Vanishing is not.

The mapping needed is cheap, and this is what makes the item worth doing rather
than pinning. A coarse chunk keeps the same path and drops the depth, so
`joinPath` places its lattice at exactly the fine lattice scaled by a power of
two: fine `(i, j)` falls in the coarse cell at `(i >> lod, j >> lod)`, and a
layer counts from the same crust top with a block twice as tall per level, so
fine layer `L` falls in coarse layer `L >> lod`. Three shifts, no search.

What the mapping does not settle is what happens when many fine cells land on
one coarse cell — `4 ^ lod` cells across and `2 ^ lod` down, so 8 fine cells
become 1 at the first level out and 512 at the third.

### Candidates

**A — Records are re-bucketed into the coarse chunk, with a precedence rule.**

Shift each of the chunk's records to the level being built and write it in. The
rule for a collision decides what the world looks like from a distance, so it is
the real content of this candidate: **a placed block beats a broken one.** A
coarse cell holding any solid edit is solid; it reads as air only when every
fine edit inside it was a break. So a wall stays a wall at distance and a
one-block hole dug in a hillside fills in, which is the right way round — a
structure is what somebody wants to see from far off and a small hole is not.

What it costs: a built object grows to the coarse cell it lands in, so a single
placed block reads as an 8 m cube two levels out. Detail is lost by design; the
question is whether it is lost in a way that looks deliberate.

**B — A chunk holding any record is not drawn coarser than it can carry.**

Pin it, or cap it a level or two out. Exact — every block is exactly where it
was put, at any distance — and it costs draw budget in proportion to how much
has been built, which is unbounded in a way nothing else in the renderer is.
A city would hold its whole footprint at full detail out to the horizon.

## I-8 — The deepest layer of the crust breaks like any other

**From:** [F-043](../FINDINGS.md), pulled in at the owner's instruction
**Step:** 1

### The problem

The crust is a shell: it runs from the planet's tallest ground down a fixed
number of layers, and under the last one there is no world at all. On the
shipped settings that floor sits 360 m under sea level. Every layer of it is
ordinary stone, so breaking the deepest one opens a hole through the bottom of
the planet.

That has cost nothing so far because nothing could break a block. This is the
release where it stops being theoretical, and a hole cannot be repaired in a
store that already has one.

### What it needs

A block type the edit path refuses to remove, written into the deepest layer of
every column by `fillColumn`. The refusal sits beside the one invariant 15
already requires for the twelve pentagon columns, so the edit path grows one
comparison rather than a second kind of rule.

Refusing by layer number instead would be cheaper still and invisible to a
player, who would meet an unbreakable block that looks exactly like the
breakable one above it. A type has a name, a color, and a rule a player can
learn by trying once.

The type is an eighth entry in `BlockType`, which is the event I-6 is about.

## Findings offered and not taken

**F-006 — the chunk store and the residency budget are written and unused.**
The entry ends by asking whether a delta store or a physics query will want
blocks resident on the thread that draws, and says that if so, `ChunkStore` is
the right shape and should carry a note. I-2 is that question arriving:
`blockAtPosition` is the physics query, and under candidate A the drawing thread
holds records rather than chunks. Pulling it in is a decision and a comment
rather than code — either `ChunkStore` gets its note or it comes out.

**F-012 — every chunk build allocates and discards half a megabyte of blocks.**
Filling a view is 200 to 330 chunk builds, each a fresh 478 KB array, and the
entry files it as a suspicion because the profile never pointed at the
collector. An edit re-generates and re-meshes one chunk per click, so the same
allocation stops being a load-time cost and becomes a cost paid while a player
is building. Pulling it in is the entry's own remedy — one reused buffer per
worker — plus a measurement either way.
