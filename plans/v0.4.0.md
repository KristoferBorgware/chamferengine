# v0.4.0

Minor: the world becomes editable. A block placed and a block broken, written
down, and still there when the page is opened again.

Everything before this release is a pure function of the seed. This one adds the
first thing that is not: a record of what a player did, held beside the terrain
and laid over it every time a chunk is built.

**Storage is the browser's own database and nothing else.** There is no server
here, local or hosted, and standing one up would be the larger half of the work
for a release whose point is the edit path. What that costs is stated rather
than hidden: a browser can clear its own storage, so a world lives as long as
the browser lets it. [`ARCHITECTURE.md`](../ARCHITECTURE.md) puts the local
server in 0.5.0 and the hosted one in 1.0.0, and both read the same records.

---

## Done when

- Aiming at a hexagon draws a wireframe hexagon over it.
- Clicking places a block against the face being aimed at. The type is picked at
  random.
- Clicking the other button removes the hexagon being aimed at.
- Reloading the page rebuilds the planet from the seed and both changes are
  still there.

## What is already decided, and is not being decided again

[Doc 27](../docs/27-block-state.md) owns block state and settles most of the
shape of a record before this release opens.

| Decided | Where |
|---|---|
| A block state is 12 bits of type and 4 of rotation, 16 in total | [doc 03](../docs/03-addressing.md), [doc 27](../docs/27-block-state.md) |
| A record on disk is `[address 29][layer 11][state 16]` = 56 of 64 bits | [doc 27](../docs/27-block-state.md) |
| The planet is not in the record — the store already belongs to one | [doc 27](../docs/27-block-state.md) |
| A block type number is a position in a list, never a hash of its name | [doc 27](../docs/27-block-state.md) |
| An explicit *air* entry is meaningful: never touched and mined out differ | invariant 6 |
| Writing a block clears that cell's side data | [doc 27](../docs/27-block-state.md) |
| The twelve pentagon columns refuse placement and removal at every layer | invariant 15 |
| An edit names a cell and a resulting block state, never an outcome | [doc 30](../docs/30-authority-and-cheating.md) |

The last two are requirements on the edit path rather than candidates. The
pentagon refusal is a comparison against `degree`, which
`chamfer/addressing` already answers; the edit shape is what keeps a validating
server from being a protocol change later.

## I-1 — What one change to the world is

**From:** the release goal
**Step:** 1

### The problem

Doc 27 fixed the record's fields and left the store's shape open. The store is
what decides how much of the address a record still has to carry, because
whatever the key already names, the record can drop.

Two numbers set the frame. A cell word is `30 + 2 x depth` bits — 52 at the
shipped depth 11, 56 with the layer and the state — which is past the 53 bits a
JavaScript `number` counts exactly, so anything carrying the whole word is two
32-bit halves or a `bigint`, the way `CellId` already is. And a chunk at depth 11
and chunk level 6 holds 561 slots, which is 10 bits, so a cell's place *inside*
its chunk is far smaller than its place on the planet.

### Candidates

**A — One row per chunk, records carrying the whole cell word.**

The key is the chunk's own key, the face and path packed the way `ChunkAddress`
already packs them. The value is a `Uint32Array` of pairs: every record 8 bytes,
the 56-bit word split into the two halves `CellId` uses. A chunk's changes
arrive as one read at exactly the moment the mesher asks for that chunk.

This is the shape [`ARCHITECTURE.md`](../ARCHITECTURE.md) already states for
1.0.0 — chunk ID to a blob of deltas, one `get` and one `put` — so a hosted
store later is a swap under the same two calls rather than a re-cut of the data.
Every record says which cell it is without its key, so one can be handed to a
mesher, a probe or a wire message unchanged.

What it costs: placing one block rewrites that chunk's whole blob. At the tens
of records a chunk actually accumulates that is a few hundred bytes; a chunk
somebody has spent a day in holds a few thousand and rewrites tens of kilobytes
per click.

**B — One row per chunk, records relative to it.**

The same key, and the record drops everything the key repeats:
`[slot 10][layer 11][state 16]` is 37 bits, inside the 53 a `number` counts
exactly. One plain number per record, no halves, no `bigint` anywhere on the
edit path, and 5 bytes of meaning where A spends 8.

What it costs is the chunk level. `slot` is `rank(q, r)` and `rank` is a
function of `m`, which is `2 ^ (depth - chunkLevel)` — so the chunk level is
baked into every record. `verification/id.js` already priced that on the
addressed form: move the chunk level and 2,144 of 2,145 cells change value,
which is what made doc 06's *tunable after launch* false and what pushed doc 03
to option C. The key bakes the chunk level under either candidate; the
difference is that A's records survive a re-key by being read out and re-filed,
and B's do not survive at all.

### Named and not taken

**One row per edit, keyed by the cell word**, letting the database do the
indexing: cell IDs sort into chunk order (doc 03), so a chunk's changes are a
range query. It reads well and it is the wrong shape for the store this design
is heading toward — every later version wants one blob per chunk, so this one
would be re-cut before it was used twice.

## I-2 — Where a change is applied, so the mesh and the player agree

**From:** the release goal
**Step:** 1

### The problem

The world is built in two places that never speak to each other. A mesh worker
runs `generateChunk` and meshes it, and the blocks never come back across —
`MeshResult` carries geometry and nothing else, on purpose, because a chunk is
478 KB of blocks and 210 KB of geometry. Meanwhile the thread that draws holds
its own `TerrainGenerator` and asks `blockAtPosition` for collision and for
whether the player is swimming.

So a placed block that only the worker knows about is one the player walks
through, and one only the main thread knows about is one that is never drawn.

There is a second consequence with no fix in it, only a statement. Level of
detail here is **resampling, not decimation** — Goldberg levels do not nest, so
a coarse chunk re-evaluates the terrain at wider spacing rather than dropping
cells. A change at one cell therefore has no cell to land on in a coarser chunk.
A built house is visible at full detail and gone at the first coarsening, and
that is a property of the tiling rather than of the store.

### Candidates

**A — The changes travel with the job.**

The thread that draws owns the store. A mesh job for a chunk carries that
chunk's records; the worker runs `generateChunk` and then writes them over it,
before meshing. An edit re-issues the job for that one chunk. The same thread
keeps the records in a map for `blockAtPosition`, so the player and the picture
read one source.

One rule and no cases: **a chunk is generated, then patched.** The blob is sent
again whenever the chunk changes level, which at tens of records is a few
hundred bytes against 210 KB of geometry coming the other way.

**B — Every worker holds the store.**

Workers open the database themselves and keep a resident map. An edit is
broadcast to all of them and to the drawing thread. Nothing rides on the job.

What it costs is coherence: as many copies as there are cores, all of which must
have the write before the re-mesh, so an edit becomes a round of messages with
an ordering requirement rather than one job with a payload.

## I-3 — Which hexagon the player is looking at

**From:** the release goal
**Step:** 1

### The problem

[Doc 09](../docs/09-ray-traversal.md) designs block picking as a grid walk and
nothing implements it. There is no ray in the engine at all: the client turns a
camera into a matrix and a frustum, and the only thing that ever asks where a
point sits is `positionToCell`.

Both breaking and placing need the same walk, and placing needs one thing more
than breaking does. Breaking wants the first solid cell along the look
direction. Placing wants the last empty cell before it, which is where the new
block goes — so aiming at the side of a wall puts the block beside it rather
than on top.

### Candidates

**A — Build doc 09's walk.**

Step cell to cell: pick the neighbour the ray leaves through, cross a face edge
where it comes to one, step a layer where it crosses a layer boundary. Exact by
construction, and it names the face the ray crossed, so the placement cell falls
out of the walk rather than being inferred.

It is the larger piece of work in this release, and its edge cases are the ones
this project already knows are sharp: crossing between faces mid-walk, arriving
at a pentagon where the ring is five long, and interleaving the horizontal step
with the radial one.

**B — March the ray in fixed steps.**

Walk out from the eye a fraction of a block at a time, ask `positionToCell` at
each step, stop at the first solid cell. The cell held at the step before is the
placement cell, so both answers come out of one loop.

Reach is a few metres, so a tenth-of-a-block step is on the order of fifty
lookups once a frame. What it costs is exactness: a step that cuts a corner
misses a cell the walk would have entered, and the miss shows up as picking the
block behind the one you aimed at rather than as an error. It is also a
lookalike of a walk this project has already designed, which is the thing
[`HOW-TO-WRITE-PLANS.md`](../HOW-TO-WRITE-PLANS.md) warns about — and the walk
has a second caller waiting for it, since doc 25 requires a swept segment rather
than an endpoint for a falling player.

## I-4 — The marker over the hexagon

**From:** the release goal
**Step:** 1

### The problem

Aiming has to be visible before clicking is safe, and a hexagon on a sphere is
not where a square-grid reflex expects it. `cellCorners` already returns a
cell's six corners, and `MarkerRenderer` already draws a line list with a
position and a color per vertex, so the geometry and the pipeline both exist.

### Candidates

**A — The top ring.** Six lines around the top face of the hit cell, lifted
clear of the surface by a fraction of a block so the depth test does not fight
the ground it sits on. Reads as *this surface*.

**B — The whole cell as a prism.** Top ring, bottom ring and six verticals —
eighteen lines. Reads as *this cell*, which is the question being asked when the
ray hits a wall rather than a floor, and it also shows which way the cell is
turned.

## I-5 — Which world a set of changes belongs to

**From:** the release goal
**Step:** 1

### The problem

Doc 27 says the planet is not in the record because the file already belongs to
one planet. There is no file here. There is a browser database and a query
string full of knobs, and several of those knobs move the ground the blocks
were put on.

`trial-knobs.ts` already measured which ones reach a coastline: Land moves the
land-or-sea state of 25 to 50% of cells across its range, Landform across 17%,
Radius 16%, and every other knob 0%. Coastline is not the question here —
whether a cell holds ground is — but it says the same thing about the shape of
the problem: a few knobs move everything and most move nothing.

### Candidates

**A — Key on the seed and the shape.** Seed, subdivision depth, block size and
crust depth: the numbers that decide where a cell *is*. Terrain knobs then move
the ground under existing blocks and the blocks stay where they were put, which
can leave a wall standing in the air. Honest about what a change of scenery
does, and it keeps one world across knob-twiddling.

**B — Key on every knob that decides the ground.** Any change puts the player
in a different world with its own empty store, so nothing is ever left hanging.
The key is derived rather than stored, so setting the sliders back reaches the
same store again exactly. What it costs is that nudging a slider to look at
something walks away from a build, with no warning at the moment it happens.

## I-6 — Whether the store carries a block registry

**From:** [doc 27](../docs/27-block-state.md), and `BlockType.ts`'s own note
**Step:** 1

### The problem

`packages/engine/src/generation/terrain/BlockType.ts` carries seven numbered
types and a line saying doc 27's registry replaces the list once a save format
exists. This release is where one starts existing.

Doc 27's rules are three: append only, never reuse a slot, the store carries the
names. A full 4,096-entry registry is about 96 KB, and this world has seven
entries in it.

### Candidates

**A — Write the registry now.** The store gets a header holding the names in
order, and loading reads the numbers back through it. Costs a header format and
one comparison at load. Buys a store that says what its own numbers meant, on
the day the seventh type stops being the seventh.

**B — Defer it, and record why.** Seven types, one build, no mods and no other
machine. The numbers are the enum's, the enum is in the source, and a store
written this week is read by the same build. The header goes in when the type
list first changes, and until then the release carries a version number and
nothing else.

This item is offered rather than assumed. It is doc 27's work rather than this
release's, and pulling it in widens the scope by a header format and a load
path.

## Findings offered

Three entries in [`FINDINGS.md`](../FINDINGS.md) sit in the code this release
opens. None is pulled in.

**F-043 — nothing says the bottom layer of the crust cannot be dug through.**
The crust is a shell and under its last layer there is no world. Every layer of
it is ordinary stone, so breaking the deepest one opens a hole through the
bottom of the planet. That has cost nothing so far because nothing could break a
block; this is the release where it stops being theoretical. The fix the entry
names is a block type the edit path refuses to remove, written into the deepest
layer of every column — one comparison next to the pentagon refusal invariant 15
already requires, and a name in the registry I-6 is about. Pulling it in adds a
type, a line in `fillColumn` and a line in doc 06.

**F-006 — the chunk store and the residency budget are written and unused.**
The entry ends by asking whether a delta store or a physics query will want
blocks resident on the thread that draws, and says that if so, `ChunkStore` is
the right shape and should carry a note. I-2 is that question arriving:
`blockAtPosition` is the physics query, and under candidate A the drawing thread
holds records rather than chunks. Pulling it in is a decision and a comment
rather than code — either `ChunkStore` gets its note or it comes out.

**F-012 — every chunk build allocates and discards half a megabyte of blocks.**
Filling a view is 200 to 330 chunk builds, each a fresh 478 KB array, and the
entry files it as a suspicion because the profile never pointed at the
collector. An edit re-generates and re-meshes one chunk per click, so the same
allocation stops being a load-time cost and becomes a cost paid while a player
is building. Pulling it in is the entry's own remedy — one reused buffer per
worker — plus a measurement either way.
