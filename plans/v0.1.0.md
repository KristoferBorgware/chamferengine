# Implementation plan — v0.1.0

Internal working document. It says what gets built, in what order, and what
"done" means for each piece. The reasoning behind every design decision lives in
`docs/`; this page cites it and does not repeat it.

One plan per release. `v0.2.0` gets its own page when this one closes.

---

## What v0.1.0 is

**A rendering and performance test.** A generated planet with continents, rivers
and oceans, walkable at ground level and viewable from space, running at frame
rate, deployed to GitHub Pages with a seed entry page.

This is a subset of [`ARCHITECTURE.md`](../ARCHITECTURE.md)'s **0.5.0**
milestone. Those two number different things: `0.5.0` is a deployment shape
(local client, local server, filesystem storage), while `0.1.0` is a release.
Releases `0.1.0` through `0.4.x` build toward `0.5.0`; `0.1.0` reaches for the
client half and stops before the server exists at all.

### In scope

| | |
|---|---|
| Planet | generated from a seed, level 11, 1 m cells, radius 1,700 m |
| Landmasses | continents, decided before rivers |
| Rivers | flow routing and erosion over a coarse map, computed at world creation |
| Water | a translucent block type with no collision, placed by the generator |
| Ground | walk at 1.4 m/s, gravity toward the centre, terrain collision |
| Swimming | float in water, walk out at the shore |
| Flight | free movement at higher speed, no collision |
| Space | pull back to orbit and look down at the whole planet |
| Teleport | by entered latitude/longitude/altitude, and to named places |
| Named places | the twelve pentagons, the two coordinate poles |
| Colour | one flat colour per cell, from material and height |
| Light | sun, sky light down a column, ambient occlusion, day/night |
| Sky | world-fixed stars, atmospheric scattering, clouds, moon |
| Deployment | GitHub Action to Pages, landing page, documentation beside it |

**Translucency is in from the start.** Transparency is the one thing a renderer
finds genuinely hard, and [doc 14](../docs/14-meshing-and-lod.md) carried it as an
open question until [doc 25](../docs/25-water.md) closed it. Project 3 draws a
translucent surface before any terrain exists, so the pass is proven before the
mesher depends on it.

Each of these is designed in `docs/` and deliberately deferred.

| Multiplayer, interest management, any server | [22](../docs/22-multiplayer-interest.md), [29](../docs/29-what-runs-where.md), [30](../docs/30-authority-and-cheating.md) |

| Ray traversal and block picking | [09](../docs/09-ray-traversal.md) |
| Pathfinding | [10](../docs/10-pathfinding.md) |
| Directional blocks, rotation states | [19](../docs/19-directional-blocks.md) |

Ground collision samples the cell under the player and the one below it, which
is [doc 04](../docs/04-position-lookup.md)'s position lookup plus a solidity
read. A falling player is tested against every layer crossed rather than the
endpoint, which is a walk down one column — invariant 10 makes a column straight.
Neither uses [doc 09](../docs/09-ray-traversal.md)'s ray walk, which crosses
cells horizontally.

### The target

**60 frames per second at 1920×1080**, on a mid-range discrete GPU, in every
reference scene in Project 16.

Nothing in the specification has measured a whole frame, in any language
([doc 28](../docs/28-language-and-runtime.md) says so directly). Project 16
produces that measurement, and every number it contradicts gets corrected in
`docs/` rather than worked around here.

## Package layout

Five packages under `packages/`, npm workspaces, one source tree.

| Package | Holds | Depends on |
|---|---|---|
| `@chamfer/core` | addressing: IDs, the lattice, neighbours, `rank` | — |
| `@chamfer/generation` | noise, the coarse map, the height field, solidity | `core` |
| `@chamfer/mesh` | surface extraction, geometry, ambient occlusion | `core`, `generation` |
| `@chamfer/render` | WebGPU device, pipelines, passes, sky | `core` |
| `@chamfer/client` | camera, input, player, UI, the two pages | all |

The split follows [`ARCHITECTURE.md`](../ARCHITECTURE.md)'s four parts.
`core` is addressing, `generation` is the part that must be bit-identical
between clients, and `mesh` plus `render` plus `client` are presentation. World
state has no package because v0.1.0 stores nothing.

`mesh` holds no WebGPU type. It writes through a sink interface it declares
itself, per [`CODE-STYLE.md`](../CODE-STYLE.md), so it runs under plain Node in
tests with no GPU present.

## Project 1 — Repository and toolchain

### Step 1.1 — Workspace root

- `package.json` with `"workspaces": ["packages/*"]` and
  `"engines": { "node": ">=22" }`.
- `.nvmrc` pinned to `22`.
- `tsconfig.base.json`: `strict`, `ES2022`, `bundler` resolution, project
  references between the packages.
- `.prettierrc` with `tabWidth: 4` and `useTabs: true`, per
  [`CODE-STYLE.md`](../CODE-STYLE.md).
- `.gitignore` gains `node_modules/`, `dist/`, `.vite/`.

Two constraints on the root, both of which bite silently:

- **The root declares no `"type": "module"`.** Each package declares it
  individually. Setting it at the root makes Node read `tools/*.js` and
  `verification/*.js` as ESM, and every one of them uses `require`.
- **Prettier covers `packages/` only.** `.prettierignore` excludes `*.md`,
  `.github/`, `docs/`, `demos/`, `verification/` and `tools/`, which are
  hand-wrapped prose and zero-dependency scripts with their own layout.

### Step 1.2 — The five packages

Each gets `package.json`, `tsconfig.json` extending the base, and `src/index.ts`.
Internal packages resolve to TypeScript source, so there is no build step
between them during development.

### Step 1.3 — The Vite app

- Two HTML entry points in `packages/client`: `index.html` is the landing page,
  `planet.html` is the engine.
- `vite.config.ts` with both as Rollup inputs and `base` set for Pages.

### Step 1.4 — Scripts

`dev`, `build`, `preview`, `typecheck`, `format` and `format:check` at the root,
plus `docs`, `figures`, `reference` and `coverage` wrapping the existing tools.
A `test` script arrives with the runner decision in Open questions.

The existing `tools/` scripts stay plain Node with no dependencies and keep
running exactly as they do now.

**Done when** `npm install`, `npm run dev`, `npm run typecheck` and `npm run
build` all succeed on a clean checkout.

## Project 2 — Core: math and addressing

`@chamfer/core`. Everything here is integer work plus one barycentric blend and
one `normalize`. No noise, no terrain.

### Step 2.1 — Numeric primitives

- `Vec3` in `float64`.
- `normalize` written as `sqrt(x*x + y*y + z*z)`. Never `Math.hypot`, which
  differs by 1 ULP between runtimes ([doc 28](../docs/28-language-and-runtime.md)).
- A lint rule banning `Math.hypot` in `core` and `generation`.

### Step 2.2 — The icosahedron

- 12 vertices, 20 faces as vertex triples, 30 edges, face centroids.
- The polar axis: vertices `0` and `3`, north at `0`, prime meridian through
  `v11` ([doc 20](../docs/20-player-coordinates.md)). Never change any of the three.
- Assert the counts and that all 30 edges are one length.

### Step 2.3 — The ID word

- Layout `[planet 12][face 5][path 2D][corner 2][layer 10]`, 51 of 64 bits at
  D11 ([doc 03](../docs/03-addressing.md), `id.js`).
- 51 bits fits inside `float64`'s exact integer range, so an ID is a plain
  `number`. JavaScript's bitwise operators are 32-bit, so field extraction uses
  multiply and divide or a split into two 32-bit halves. Pick one and keep it.
- Encode, decode, truncate to a chunk prefix.
- Canonicalise by lowest ID — encoding option C, verified in `id.js` §5–6.

### Step 2.4 — Lattice coordinates

- `(i, j)` across a face, `(q, r)` within a chunk, and the round trip through
  path digits, including the flip bit (`qr.js`).
- The middle-child flip is a **half turn**: it negates both axes, determinant
  `+1`, so nothing is ever mirrored (`winding.js`).
- `rank(q, r) = q + r·(2m+3−r)/2`, with `m = 2^(D−C)` (`rank.js`).
- Chunk slots `(m+1)(m+2)/2` = **561** at D11/C6, a uniform stride for every
  chunk.
- Border ownership: the lowest chunk ID containing a cell owns it.

### Step 2.5 — ID to position

- One-shot barycentric: `(i, j)` maps to `normalize(A·a + B·b + C·c)`, evaluated
  once at full depth (invariant 12). Repeated arc-midpoint subdivision produces a
  different sphere, off by 38.97 m on the worked planet.
- Cell corners are lattice points at `3n`: `(3i+2, 3j+1)` for an up-triangle and
  `(3i+1, 3j+2)` for a down-triangle. Average the flat lattice points, then
  project (invariant 14, [doc 18](../docs/18-cell-boundary.md)).

### Step 2.6 — Position to cell

The four-step pipeline from [doc 04](../docs/04-position-lookup.md):

```
dir     = normalize(pos)
face    = argmax over the 20 centroids of dot(dir, centroid)
(a,b,c) = barycentric of dir in that face
(i,j)   = hexRound(a*n, b*n, c*n)
layer   = floor((surfaceRadius - |pos|) / blockSize)
```

Nearest centroid **is** the containing face, exactly. `hexRound` repairs the
coordinate that moved furthest.

### Step 2.7 — Neighbours

- The 60-entry, 180-byte face adjacency table (`adj.js`).
- `neighbour(id, k)` from the table and integers alone (`neighbour.js`).
- Direction index `0` is the step from the face's `A` toward `B`, the `(i, j)`
  offset `(+1, 0)`. Never derived from `(q, r)` sign.
- Face crossing is three additions: `(α,β,γ) → (α+γ, β+γ, −γ)`.
- A pentagon's ring is **5** long. `k = 5` is not a direction, not a duplicate,
  and not a null.

### Step 2.8 — Tests against the verification scripts

`verification/` already holds reference implementations and recorded outputs for
`hexRound`, `rank`, `neighbour`, the ID word and the noise kernel. The engine's
tests assert agreement with those recorded numbers.

**Done when** every check in `lookup.js`, `qr.js`, `winding.js`, `rank.js`,
`neighbour.js` and `id.js` passes against the engine's own implementation.

## Project 3 — First light

A vertical slice that proves the toolchain, WebGPU and Project 2 together. No
terrain.

### Step 3.1 — Device bring-up

Adapter, device, canvas context, preferred format, resize handling, error
scopes. A missing WebGPU implementation produces a readable message rather than
a blank page.

### Step 3.2 — Camera

Perspective projection, view from a position and orientation. `float64` in the
world, `float32` at the GPU boundary, chunk-relative (invariant 13).

### Step 3.3 — Draw the bare lattice

Every cell at level 4 — 2,562 of them — as one flat-coloured hexagon, coloured
by face index.

### Step 3.4 — A translucent shell

A second sphere at a slightly larger radius, drawn in a translucent pass over
the first: depth test on, depth write off, alpha blending, drawn after the
opaque pass. It stands in for Project 9's water and proves the pass works before
anything depends on it.

**Done when** a Goldberg sphere rotates on screen with all twelve pentagons
visible, no seams at the 30 face edges, no inside-out triangles, and the
translucent shell reads correctly over it from every angle. This one scene
exercises the ID word, the corner rule, the projection, the winding rules and
the blend state at once.

## Project 4 — Noise and the seed

`@chamfer/generation`. Pure functions of the seed and a position. No I/O, no
allocation, no clock, no transcendentals ([doc 23](../docs/23-determinism.md)).

### Step 4.1 — The seed

A seed is correct here and is already what the design assumes: terrain is a pure
function of position and a seed, and persistence is a seed plus a delta store
([doc 07](../docs/07-data-structures.md)).

The engine accepts a **string** and reduces it to a `uint32` with the same
integer hash the noise uses. Strings make shareable URLs; the `uint32` keeps the
arithmetic integer-only. [Doc 03](../docs/03-addressing.md)'s 12-bit planet field
is a separate thing and stays fixed at `0`.

### Step 4.2 — The noise kernel

Pinned by [doc 08](../docs/08-terrain-generation.md) and `noise.js`:

- Hash: 3 wrapping `uint32` multiplies and 2 xor-shifts, divided by `2^32`. In
  TypeScript that is `Math.imul` with a `>>> 0` after each step.
- Fade: **quintic** `6t⁵−15t⁴+10t³`. Smoothstep jumps curvature by 12 at every
  lattice plane, which shading shows as a grid.
- Trilinear value noise in 3D.
- fBm: lacunarity 2, gain 0.5, **low octave first**, divided by summed
  amplitude. The order is fixed; reversing it moves the result by `1.4e-17`.

**Done when** the engine reproduces `noise.js`'s recorded digest exactly.

## Project 5 — Continents, rivers and erosion

The coarse map, from [doc 21](../docs/21-rivers-and-erosion.md) and `rivers.js`.
Computed once at world creation and read as an input, so the runtime generator
stays a pure function of position. 2.5 MB at level 8.

v0.1.0 has no storage, so the map is computed in a worker at startup and held in
memory. A client regenerates it from the seed rather than downloading it, which
is what [doc 22](../docs/22-multiplayer-interest.md) assumes anyway.

### Step 5.1 — Continents first

**Continents decide rivers.** The same routing gives a 31-cell river on small
blobs and 86 on a large landmass, so the continent tier is built before anything
downstream of it.

### Step 5.2 — Flow routing

Each coarse cell drains to its lowest neighbour.

Flow routing needs **no pentagon case and no face case** — 0 of the 12 pentagons
came out as pits. The coarse lookup masks the low bits of **`(i, j)`**, not the
path digits; path digits name a triangle rather than a cell.

### Step 5.3 — Pit filling

This is where the work is. A flat filled lake stops every river that reaches it;
filling with a **tiny slope** instead leaves 0 dead ends.

### Step 5.4 — Erosion

Erosion exponents come from `{0.5, 1, 1.5, 2}` only — each is a product of
`sqrt` and multiply, so the arithmetic stays inside the operations IEEE 754 pins
([doc 23](../docs/23-determinism.md)).

Routing is not the hair trigger it looks like: one ULP reroutes 0 of 40,962
cells, and nothing moves until `1e-3`.

### Step 5.5 — Read-only from here on

The coarse map states where water flows across the **generated** world. Nothing
at run time rewrites it ([doc 24](../docs/24-edits-and-global-processes.md)).
With no player edits in v0.1.0 this costs nothing, and it keeps the map a pure
function of the seed.

**Done when** a seed produces continents with rivers that reach the sea, and the
same seed reproduces the same map on a second run.

## Project 6 — Terrain: height, solidity, water and material

### Step 6.1 — The height field

Sampled in **3D world space** from the cell's direction, never from face-local
`(i, j)` (invariant 4). The coarse map from Project 5 supplies the continent and
river terms; noise supplies the detail.

### Step 6.2 — Solidity

`solid(cell)` compares the cell's layer against the height at its direction. One
height-field evaluation, no storage.

### Step 6.3 — Water placement

Water is a **block type**: translucent, no collision, written by the generator,
never simulated ([doc 25](../docs/25-water.md)). There is no fluid system, no
flow, no level-seeking and no water surface primitive.

The rule is one line: below the water surface and above the ground, place water.
Sea level is a radius; river surfaces come from Project 5.

On the worked planet that gives 69.2% of columns holding water and 1,589,689
water cells.

### Step 6.4 — The density term

Caves. Gated behind a measurement: it costs **51×** the height term over a full
crust (`volume.js`), and it only carves enclosed voids when its noise gradient
exceeds 1. Build it, measure it, and keep it only if Project 16's budget holds.

### Step 6.5 — Material and colour

One flat colour per cell from material band, height and slope. Deterministic,
integer-seeded, no texture sampling.

## Project 7 — Chunks and residency

### Step 7.1 — Chunk identity

A chunk is one triangle at `chunkLevel` 6. It holds a uniform **561** slots and
addresses them as `index = rank(q,r) × layerCount + layer`. The 8.7% of slots a
chunk does not own is the price of that uniform stride, and it is paid
deliberately (`rank.js`).

### Step 7.2 — Chunk generation

`(seed, chunkId, level)` to typed arrays. Typed arrays throughout, never an
array of objects — measured at **15×**, larger than any language gap in the
study ([doc 28](../docs/28-language-and-runtime.md) §5).

### Step 7.3 — The worker pool

Generation runs off the main thread. `hardwareConcurrency − 1` workers, results
returned as transferable typed arrays. The coarse map from Project 5 is shared
into each worker rather than recomputed.

### Step 7.4 — Residency

Which chunks are needed, given camera position and altitude. LRU eviction under
a stated memory budget.

## Project 8 — The mesher

`@chamfer/mesh`. No WebGPU types anywhere in this package.

### Step 8.1 — Surface extraction

A face is emitted where a solid cell meets a non-solid neighbour, across all six
sides plus up and down. Target is **2 vertices and 4 triangles per cell**
unmerged — exactly 2× a cube surface (`mesh.js`).

Water culls by the same rule stone does: a water cell surrounded by water emits
nothing. That is what takes 12,717,512 naive faces down to **113,455 — 0.89%**.

### Step 8.2 — Geometry

- Corners from Step 2.5: average the flat lattice points, then project.
- Chunk-relative `float32`, which gives 122 µm at radius 1,700 m
  (`precision.js`).
- Up-triangles and down-triangles need **different emit patterns**. Listing a
  downward triangle by the same rising-index rule as an upward one winds it
  inward and holes the mesh (`winding.js`).
- A pentagon has 5 corners and 3 triangles.

### Step 8.3 — Vertical run-length merging

Exact, and it follows from invariant 10: the tessellation is identical at every
layer, so a column is straight. The rectangle-growing half of greedy meshing has
no hexagonal equivalent and is not attempted.

Water's exposed top faces all sit at one radius, so they merge to doc 14's full
curvature limit — **37 cells into one quad**.

### Step 8.4 — Two buffers per chunk

Opaque and translucent geometry go into separate buffers, because Project 9
draws them in separate passes.

### Step 8.5 — The sink

`mesh` declares the interface it writes through. `render` implements it. This is
what keeps the mesher testable under plain Node.

### Step 8.6 — Ambient occlusion

Per-vertex, from the cells touching each corner. A hexagon corner is shared by
three cells rather than a cube's four, so the cube-world AO tables do not carry
over.

## Project 9 — Translucency and the water pass

Proven in outline by Step 3.4; here it meets real geometry.

### Step 9.1 — Two passes

Opaque first, then water back to front. Depth test on for both, depth write off
for the translucent pass.

### Step 9.2 — The sort is of one thing

A view crosses **one** water surface 82.3% of the time and two 0.6%, worst case
3, because water fills a column from the floor up. Sorting is per chunk, not per
triangle: the surfaces do not interpenetrate.

Generated water has **zero exposed vertical sides** — it is always held in by
land at or above its own level.

### Step 9.3 — Underwater

The camera inside a water cell needs a tint and the far plane pulled in. This is
a cell test on the camera position, which is Project 2's lookup.

**Done when** an ocean, a lake and a river all read correctly from above the
surface, at the shore, and from underneath.

## Project 10 — LOD and seams

This is what makes the space view possible, and it is the hardest project here.

### Step 10.1 — Level selection

By distance and altitude, with hysteresis so levels do not thrash across a
boundary.

LOD is **resampling, not decimation**. Goldberg levels do not nest, so a coarse
chunk re-evaluates the terrain function at a coarser spacing rather than dropping
cells ([doc 14](../docs/14-meshing-and-lod.md)). Re-generation cuts noise cost 4×
per level as well as draw cost, which makes a LOD-2 chunk about **330×** cheaper
to build.

### Step 10.2 — Far chunks run the height field alone

The density term is dropped beyond a threshold. A coarse mesh cannot represent a
cave anyway — a 3 m cave is gone by level 10.

### Step 10.3 — Seam ownership

The finer chunk owns the seam: it emits a face wherever its solidity differs
from the coarse neighbour's, in both directions. That costs 2.7 faces and one
height-field evaluation per rim column, and it closes **1041** holes that a naive
join leaves and **961** that a skirt alone leaves (`seam.js`).

Skirts stay as well, as cover for the frames after a neighbour changes level.

### Step 10.4 — The space view

At orbit the whole planet renders at a coarse level: 10,242 cells at level 5,
163,842 at level 7. Against 41,943,042 at level 11.

**Done when** the transition from eye height to orbit and back holds frame rate
with no visible holes at any seam.

## Project 11 — Lighting and ambient occlusion

Light is a scalar, so holonomy and the pentagon direction deficit do not apply to
it at all ([doc 16](../docs/16-lighting.md)).

### Step 11.1 — Sky light

Radial, down a column, monotone. Invariant 10 makes a column straight, so this is
as cheap as it is in a flat world. Stored **per column**, which is 32× smaller
than per cell.

### Step 11.2 — Sun and terminator

One dot product against gravity's `up`. The terminator moves at
`circumference / dayLength`, which is 1.4 m/s at the 2.12 hour walk time — so a
player outwalks the sun for any day shorter than that, and can hold a sunset in
place by walking west.

### Step 11.3 — Shading

Flat cell colour times light times ambient occlusion. No textures in v0.1.0.

Light storage is 4× the block data, halved again by the per-column rule. Budget
for it in Project 7's residency numbers.

## Project 12 — Sky, atmosphere and clouds

All presentation, so this is where the transcendentals
[doc 23](../docs/23-determinism.md) keeps out of the generator are spent
([doc 32](../docs/32-sky-clouds-and-moon.md)).

### Step 12.1 — The skybox is world-fixed

Walking turns your own `up` by `s/R` — 3.37° per 100 m, and a full 360° over the
10,681 m circumference. A view-fixed skybox makes the stars follow the player
around the planet.

### Step 12.2 — Atmospheric scattering

Correctly scaled air gives a zenith optical depth of `6.4e-5` against Earth's
`0.241` — **3,748× too thin**, and a black daytime sky. Angles scale and path
lengths do not.

So the scattering model runs on a **fictional Earth-sized atmosphere**. Preetham,
Hosek-Wilkie and Bruneton are all parameterised by radius and scale height; feed
them Earth's. Take only the sun direction from the real world.

### Step 12.3 — Clouds

Clouds borrow the lattice and are **not cells**. A cloud has no cell ID, no
chunk, and no layer — `layer` counts downward from the crust top, so there is no
value it could take.

A cloud is a lattice point indexed by `(face, i, j)` into a transient buffer, the
way a vertex is rather than the way a block is. Level 5 gives a 64 m puff and
10,242 points for the whole sky, under 9% of them in view at 300 m.

### Step 12.4 — Wind

**One axis and one rate**, rotating the sample point before the noise lookup. The
hairy ball theorem forbids a uniform wind. Of the two obvious fields only rigid
rotation is divergence-free — mean `|div|` of `3.3e-12` against `0.9988` for a
projected world vector. Calm patches are 0.5% of the surface, at the axis poles.

### Step 12.5 — The moon

Angular size is an art decision; a faithfully scaled real moon is still 0.52°,
because scaling preserves angles. Its **distance** is not an art decision:
walking round the planet shifts it 1.9° against the stars, so it cannot be
painted into the skybox.

**Demo:** [`demos/sky-on-a-small-planet.html`](../demos/sky-on-a-small-planet.html)
shows all of this moving.

## Project 13 — Player, movement and frames

### Step 13.1 — The three frames

Axis for coordinates, transported for the camera, grid for machinery. They are
three frames for three jobs and must not be interconverted casually
([doc 13](../docs/13-gravity-and-orientation.md)).

### Step 13.2 — Gravity

`up` is `normalize(position)`. There is no global up and no global north — the
hairy ball theorem forbids one, so a heading is never stored as a world vector
(invariant 8).

`float32` holds `up` to 0.005″ at every radius, so directions need no precision
handling even where positions do.

### Step 13.3 — Floating origin

Anchor plus offset, offset in `float64`, which gives `7.1e-15 m` over a 32 m
chunk. Never cache a world-space position across a frame — recompute it
(invariant 13, [doc 15](../docs/15-precision-and-origin.md)).

### Step 13.4 — Walking

1.4 m/s. The ground test samples the cell the player occupies and the one below,
which is Project 2's position lookup plus a solidity read. Step up one block.

A falling player crosses 1.67 m per frame at 30 Hz, so the fall is tested
against every layer it crosses rather than against the endpoint. That is a walk
down one column, which invariant 10 makes straight.

### Step 13.5 — Swimming

Water does not collide, and floating is a different question from collision:
collision is a **face** test, floating is a **cell** test — the position lookup
plus a block-type read.

At 1 m blocks a 1.8 m player stands in one block of water and swims in two, so
walking and swimming are separated by a **threshold one cell wide**. There is no
partial-buoyancy case to write.

The generated world makes this playable without designing for it: 85.3% of the
water's edge is one block deep, a player can step out at 99.9% of shore columns,
and all 58 bodies of water have an exit.

### Step 13.6 — Flying

Higher speed, no collision, speed scaling with altitude so orbit is reachable in
reasonable time.

### Step 13.7 — Space mode

Pull back to orbit and look down. Interacts directly with Project 10 — the
transition is where LOD selection is under most pressure.

## Project 14 — Navigation and teleport

### Step 14.1 — Coordinate readout

### Step 14.2 — Teleport by coordinates

Enter latitude, longitude and altitude; arrive there.

### Step 14.3 — Named places

- The **twelve pentagons**. All sit on exact multiples of 36° of longitude, and
  the ring latitudes are `±atan(1/2)` = `±26.565°`.
- The north and south poles, which are two of those twelve.

Pentagon separation is 1,882 m and the cover radius is 1,109 m, so from any
named place another is about a kilometre away (`pentagon.js`).

## Project 16 — Performance

The point of the release.

### Step 16.1 — Instrumentation

Frame time against a 16.6 ms budget at 60 Hz, split by phase: generation,
meshing, upload, draw. GPU timestamp queries where the adapter exposes them.

World creation is measured separately. Nobody has timed the coarse map, and a
client regenerates it on load rather than downloading it — if it is slow it needs
a loading screen ([doc 29](../docs/29-what-runs-where.md)).

### Step 16.2 — Reference scenes

| Scene | What it tests | Expected load |
|---|---|---|
| Eye height, flat ground | the floor case | ~21,000 cells, 84k triangles |
| Eye height, 120 m relief | real terrain | 9.5 triangles per cell |
| Standing at the shore | the translucent pass | one surface, sorted per chunk |
| Underwater | the camera inside a water cell | tint, near geometry |
| Standing on a pentagon | the degree-5 path | one cell, every frame |
| Orbit | LOD at its coarsest | whole planet, level 5–7 |
| Terminator crossing | lighting under change | full sky light re-evaluation |
| Flying at speed | residency churn | chunk load and evict under pressure |

The 21,000 figure is a **floor**, not an estimate — it assumes flat ground, and a
60 m hill raises the visible count 47× (`volume.js`).

### Step 16.3 — Feed the results back

Every measurement that contradicts a number in `docs/` gets the document
corrected, with the script updated to match. The specification is the shared
base; where the engine proves it wrong, the engine wins and the document moves.

Three numbers are already known to need this treatment: `volume.js`, `mesh.js`
and `seam.js` still use the older noise hash and so describe a slightly different
planet — 1.28 m mean and 5.85 m worst over 60 m of relief. Their conclusions are
statistical and hold, but the scripts should switch to `noise.js`'s pinned hash
before the engine is sized against them.

## Open questions

- **The density term.** Kept or dropped on Project 16's numbers, not before.
- **A test runner.** Vitest pairs with Vite and would carry Project 2.8. It is
  the first dependency beyond Vite, TypeScript and Prettier.
- **Crust depth at run time.** The worked planet uses 64 layers against a 435
  cap. A shallower crust would cut residency cost, and nothing in v0.1.0 digs.
- **Coarse map level.** [Doc 21](../docs/21-rivers-and-erosion.md) prices it at
  level 8 and 2.5 MB. Whether that resolution gives rivers that read well at
  1 m cells is unmeasured.
