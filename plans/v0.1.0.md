# Implementation plan — v0.1.0

Internal working document. It says what gets built, in what order, and what
"done" means for each piece. The reasoning behind every design decision lives in
`docs/`; this page cites it and does not repeat it.

One plan per release. `v0.2.0` gets its own page when this one closes.

---

## What v0.1.0 is

**A rendering and performance test.** A generated planet with continents, rivers
and oceans, walkable at ground level and viewable from space, running at frame
rate, deployed to GitHub Pages with a seed entry page.

This is a subset of [`ARCHITECTURE.md`](../ARCHITECTURE.md)'s **0.5.0**
milestone. Those two number different things: `0.5.0` is a deployment shape
(local client, local server, filesystem storage), while `0.1.0` is a release.
Releases `0.1.0` through `0.4.x` build toward `0.5.0`; `0.1.0` reaches for the
client half and stops before the server exists at all.

### In scope

| | |
|---|---|
| Planet | generated from a seed, level 11, 1 m cells, radius 1,700 m |
| Crust | **435 layers**, the taper cap at `D` 11 — 6.8× the 64 the design assumes |
| Landmasses | continents, decided before rivers |
| Rivers | flow routing and erosion over a coarse map, computed at world creation |
| Water | a translucent block type with no collision, placed by the generator |
| Ground | walk at 1.4 m/s, gravity toward the centre, terrain collision |
| Swimming | float in water, walk out at the shore |
| Flight | free movement at higher speed, no collision |
| Space | pull back to orbit and look down at the whole planet |
| Teleport | by entered latitude/longitude/altitude, and to named places |
| Named places | the twelve pentagons, the two coordinate poles |
| Color | one flat color per cell, from material and height |
| Light | sun, sky light down a column, ambient occlusion, day/night |
| Sky | world-fixed stars, atmospheric scattering, clouds, moon |
| Deployment | GitHub Action to Pages, landing page, documentation beside it |

**Translucency is in from the start.** Transparency is the one thing a renderer
finds genuinely hard, and [doc 14](../docs/14-meshing-and-lod.md) carried it as an
open question until [doc 25](../docs/25-water.md) closed it. Project 3 draws a
translucent surface before any terrain exists, so the pass is proven before the
mesher depends on it.

### Out of scope

Each of these is designed in `docs/` and deliberately deferred.

| | Where it is designed |
|---|---|
| Player edits, the delta store, the block registry | [07](../docs/07-data-structures.md), [24](../docs/24-edits-and-global-processes.md), [27](../docs/27-block-state.md) |
| Multiplayer, interest management, any server | [22](../docs/22-multiplayer-interest.md), [29](../docs/29-what-runs-where.md), [30](../docs/30-authority-and-cheating.md) |
| AWS hosting | [31](../docs/31-deployment.md) |
| Ray traversal and block picking | [09](../docs/09-ray-traversal.md) |
| Pathfinding | [10](../docs/10-pathfinding.md) |
| Directional blocks, rotation states | [19](../docs/19-directional-blocks.md) |

Ground collision samples the cell under the player and the one below it, which
is [doc 04](../docs/04-position-lookup.md)'s position lookup plus a solidity
read. A falling player is tested against every layer crossed rather than the
endpoint, which is a walk down one column — invariant 10 makes a column straight.
Neither uses [doc 09](../docs/09-ray-traversal.md)'s ray walk, which crosses
cells horizontally.

### The target

**60 frames per second at 1920×1080**, on a mid-range discrete GPU, in every
reference scene in Project 16.

Nothing in the specification has measured a whole frame, in any language
([doc 28](../docs/28-language-and-runtime.md) says so directly). Project 16
produces that measurement, and every number it contradicts gets corrected in
`docs/` rather than worked around here.

## Package layout

Two packages under `packages/`, npm workspaces, one source tree.

| Package | Holds |
|---|---|
| `chamfer` | the engine, published |
| `@chamfer/client` | camera, input, player, UI, the two pages |

The engine's subsystems are folders under `src/`, reached by subpath export:

| Subpath | Holds |
|---|---|
| `chamfer/math` | vectors and matrices |
| `chamfer/world` | radius, block size, layers, the taper cap |
| `chamfer/addressing` | IDs, the lattice, neighbours, `rank`, the lookup |
| `chamfer/generation` | noise, the coarse map, the height field, solidity |
| `chamfer/light` | sky exposure, the sun, the terminator, light discs |
| `chamfer/sky` | the atmosphere, wind, clouds, the moon |
| `chamfer/player` | gravity, walking, swimming, flying, the carried heading |
| `chamfer/coordinates` | latitude and longitude, the twelve landmarks, share codes |
| `chamfer/mesh` | surface extraction, geometry, ambient occlusion |
| `chamfer/render` | WebGPU device, pipelines, passes, sky |

That follows [`ARCHITECTURE.md`](../ARCHITECTURE.md)'s four parts. `addressing`
is addressing, `generation` is the part that must be bit-identical between
clients, and `mesh` plus `render` plus the client are presentation. World state
has no subsystem because v0.1.0 stores nothing.

A subpath is what keeps the parts apart. A server imports `chamfer/addressing`
and pulls in nothing that mentions a GPU. One package rather than five keeps a
consumer on one version and lets a shared type sit where both subsystems reach
it — the reasoning is in [`CODE-STYLE.md`](../CODE-STYLE.md).

`mesh` holds no WebGPU type. `mesh/Geometry.ts` is two typed arrays and two
counts, and that is the whole contract with the renderer, so the mesher runs
under plain Node in tests with no GPU present.

## Project 1 — Repository and toolchain

### Step 1.1 — Workspace root

- `package.json` with `"workspaces": ["packages/*"]` and
  `"engines": { "node": ">=22" }`.
- `.nvmrc` pinned to `22`.
- `tsconfig.base.json`: `strict`, `ES2022`, `bundler` resolution, project
  references between the packages.
- `.prettierrc` with `tabWidth: 4` and `useTabs: true`, per
  [`CODE-STYLE.md`](../CODE-STYLE.md).
- `.gitignore` gains `node_modules/`, `dist/`, `.vite/`.

Two constraints on the root, both of which bite silently:

- **The root declares no `"type": "module"`.** Each package declares it
  individually. Setting it at the root makes Node read `tools/*.js` and
  `verification/*.js` as ESM, and every one of them uses `require`.
- **Prettier covers `packages/` only.** `.prettierignore` excludes `*.md`,
  `.github/`, `docs/`, `demos/`, `verification/` and `tools/`, which are
  hand-wrapped prose and zero-dependency scripts with their own layout.

### Step 1.2 — The packages

Each gets `package.json`, `tsconfig.json` extending the base, and `src/index.ts`.
Internal packages resolve to TypeScript source, so there is no build step
between them during development.

### Step 1.3 — The Vite app

- Two HTML entry points in `packages/client`: `index.html` is the landing page,
  `planet.html` is the engine.
- `vite.config.ts` with both as Rollup inputs and `base` set for Pages.

### Step 1.4 — Scripts

`dev`, `build`, `preview`, `typecheck`, `test`, `test:watch`, `format` and
`format:check` at the root, plus `docs`, `figures`, `reference` and `coverage`
wrapping the existing tools.

The existing `tools/` scripts stay plain Node with no dependencies and keep
running exactly as they do now.

### Step 1.5 — The test runner

**Vitest**, configured at the root over `packages/*/tests/**/*.test.ts`. A test
sits beside the file it covers and takes its name — `normalize.test.ts` beside
`normalize.ts` — per [`CODE-STYLE.md`](../CODE-STYLE.md).

Vitest shares Vite's transform pipeline, so TypeScript source runs with no
separate build and no second config to keep in step. It is the fourth dependency
after Vite, TypeScript and Prettier.

`verification/` stays outside it. Those scripts are zero-dependency plain Node
that print to stdout and are cited by `docs/`; Step 2.8 bridges the two by
asserting the engine reproduces their recorded numbers.

**Done when** `npm install`, `npm run dev`, `npm run typecheck`, `npm test` and
`npm run build` all succeed on a clean checkout.

## Project 2 — Core: math and addressing

`@chamfer/core`. Everything here is integer work plus one barycentric blend and
one `normalize`. No noise, no terrain.

### Step 2.1 — Numeric primitives

- `Vec3` in `float64`.
- `normalize` written as `sqrt(x*x + y*y + z*z)`. Never `Math.hypot`, which
  differs by 1 ULP between runtimes ([doc 28](../docs/28-language-and-runtime.md)).
- A lint rule banning `Math.hypot` in `core` and `generation`.

### Step 2.2 — The icosahedron

- 12 vertices, 20 faces as vertex triples, 30 edges, face centroids.
- The polar axis: vertices `0` and `3`, north at `0`, prime meridian through
  `v11` ([doc 20](../docs/20-player-coordinates.md)). Never change any of the three.
- Assert the counts and that all 30 edges are one length.

### Step 2.3 — The ID word

- Layout `[planet 12][face 5][path 2D][corner 2][layer 10]`, 51 of 64 bits at
  D11 ([doc 03](../docs/03-addressing.md), `id.js`).
- 51 bits fits inside `float64`'s exact integer range, so an ID is a plain
  `number`. JavaScript's bitwise operators are 32-bit, so field extraction uses
  multiply and divide or a split into two 32-bit halves. Pick one and keep it.
- Encode, decode, truncate to a chunk prefix.
- Canonicalise by lowest ID — encoding option C, verified in `id.js` §5–6.

### Step 2.4 — Lattice coordinates

- `(i, j)` across a face, `(q, r)` within a chunk, and the round trip through
  path digits, including the flip bit (`qr.js`).
- The middle-child flip is a **half turn**: it negates both axes, determinant
  `+1`, so nothing is ever mirrored (`winding.js`).
- `rank(q, r) = q + r·(2m+3−r)/2`, with `m = 2^(D−C)` (`rank.js`).
- Chunk slots `(m+1)(m+2)/2` = **561** at D11/C6, a uniform stride for every
  chunk.
- Border ownership: the lowest chunk ID containing a cell owns it.

### Step 2.5 — ID to position

- One-shot barycentric: `(i, j)` maps to `normalize(A·a + B·b + C·c)`, evaluated
  once at full depth (invariant 12). Repeated arc-midpoint subdivision produces a
  different sphere, off by 38.97 m on the worked planet.
- Cell corners are lattice points at `3n`: `(3i+2, 3j+1)` for an up-triangle and
  `(3i+1, 3j+2)` for a down-triangle. Average the flat lattice points, then
  project (invariant 14, [doc 18](../docs/18-cell-boundary.md)).

### Step 2.6 — Position to cell

The four-step pipeline from [doc 04](../docs/04-position-lookup.md):

```
dir     = normalize(pos)
face    = argmax over the 20 centroids of dot(dir, centroid)
(a,b,c) = barycentric of dir in that face
(i,j)   = hexRound(a*n, b*n, c*n)
layer   = floor((surfaceRadius - |pos|) / blockSize)
```

Nearest centroid **is** the containing face, exactly. `hexRound` repairs the
coordinate that moved furthest.

### Step 2.7 — Neighbours

- The 60-entry, 180-byte face adjacency table (`adj.js`).
- `neighbour(id, k)` from the table and integers alone (`neighbour.js`).
- Direction index `0` is the step from the face's `A` toward `B`, the `(i, j)`
  offset `(+1, 0)`. Never derived from `(q, r)` sign.
- Face crossing is three additions: `(α,β,γ) → (α+γ, β+γ, −γ)`.
- A pentagon's ring is **5** long. `k = 5` is not a direction, not a duplicate,
  and not a null.

### Step 2.8 — Tests against the verification scripts

`verification/` already holds reference implementations and recorded outputs for
`hexRound`, `rank`, `neighbour`, the ID word and the noise kernel. The engine's
tests assert agreement with those recorded numbers.

**Done when** every check in `lookup.js`, `qr.js`, `winding.js`, `rank.js`,
`neighbour.js` and `id.js` passes against the engine's own implementation.

The pentagon needs its own path. Five faces meet at an icosahedron vertex, and
two of them touch the starting face only at that vertex, so a single reflection
cannot reach their cells — the ring is built by rotating face to face around the
vertex instead. Six-step reflection is right everywhere else.

## Project 3 — First light

A vertical slice that proves the toolchain, WebGPU and Project 2 together. No
terrain.

### Step 3.1 — Device bring-up

Adapter, device, canvas context, preferred format, resize handling, error
scopes. A missing WebGPU implementation produces a readable message rather than
a blank page.

### Step 3.2 — Camera

Perspective projection, view from a position and orientation. `float64` in the
world, `float32` at the GPU boundary, chunk-relative (invariant 13).

### Step 3.3 — Draw the bare lattice

Every cell at level 4 — 2,562 of them — as one flat-colored hexagon, colored
by face index.

### Step 3.4 — A translucent shell

A second sphere at a slightly larger radius, drawn in a translucent pass over
the first: depth test on, depth write off, alpha blending, drawn after the
opaque pass. It stands in for Project 9's water and proves the pass works before
anything depends on it.

**Off by default, behind `?shell=1`.** It is scaffolding rather than scenery.

**It is deleted when the projects close.** Project 9 builds the real water pass,
and once that draws, the shell has nothing left to prove. Removing it is part of
Project 16's close, listed in *What comes out before the release* below.

**Done when** a Goldberg sphere rotates on screen with all twelve pentagons
visible, no seams at the 30 face edges, no inside-out triangles, and the
translucent shell reads correctly over it from every angle.

**The last clause needs a real GPU and is outstanding.** Headless Chromium in
this container acquires an adapter and a device, and the page reports its cell
and triangle counts, but SwiftShader drops the WebGPU instance before anything
composites, so the canvas screenshots blank. Everything below the device is
covered by tests that need no GPU: cell and triangle counts, index bounds,
winding, and the projection mapping near to 0 and far to 1. The pipeline, the
shader and the blend state are what remain unverified. This one scene
exercises the ID word, the corner rule, the projection, the winding rules and
the blend state at once.

## Project 4 — Noise and the seed

`@chamfer/generation`. Pure functions of the seed and a position. No I/O, no
allocation, no clock, no transcendentals ([doc 23](../docs/23-determinism.md)).

### Step 4.1 — The seed

A seed is correct here and is already what the design assumes: terrain is a pure
function of position and a seed, and persistence is a seed plus a delta store
([doc 07](../docs/07-data-structures.md)).

The engine accepts a **string** and reduces it to a `uint32` with the same
integer hash the noise uses. Strings make shareable URLs; the `uint32` keeps the
arithmetic integer-only. [Doc 03](../docs/03-addressing.md)'s 12-bit planet field
is a separate thing and stays fixed at `0`.

### Step 4.2 — The noise kernel

Pinned by [doc 08](../docs/08-terrain-generation.md) and `noise.js`:

- Hash: 3 wrapping `uint32` multiplies and 2 xor-shifts, divided by `2^32`. In
  TypeScript that is `Math.imul` with a `>>> 0` after each step.
- Fade: **quintic** `6t⁵−15t⁴+10t³`. Smoothstep jumps curvature by 12 at every
  lattice plane, which shading shows as a grid.
- Trilinear value noise in 3D.
- fBm: lacunarity 2, gain 0.5, **low octave first**, divided by summed
  amplitude. The order is fixed; reversing it moves the result by `1.4e-17`.

**Done when** the engine reproduces `noise.js`'s recorded digest exactly.

## Project 5 — Continents, rivers and erosion

The coarse map, from [doc 21](../docs/21-rivers-and-erosion.md) and `rivers.js`.
Computed once at world creation and read as an input, so the runtime generator
stays a pure function of position. 2.5 MB at level 8.

v0.1.0 has no storage, so the map is computed in a worker at startup and held in
memory. A client regenerates it from the seed rather than downloading it, which
is what [doc 22](../docs/22-multiplayer-interest.md) assumes anyway.

### Step 5.1 — Continents first

**Continents decide rivers.** The same routing gives a 31-cell river on small
blobs and 86 on a large landmass, so the continent tier is built before anything
downstream of it.

### Step 5.2 — Flow routing

Each coarse cell drains to its lowest neighbour.

Flow routing needs **no pentagon case and no face case** — 0 of the 12 pentagons
came out as pits. The coarse lookup masks the low bits of **`(i, j)`**, not the
path digits; path digits name a triangle rather than a cell.

### Step 5.3 — Pit filling

This is where the work is. A flat filled lake stops every river that reaches it;
filling with a **tiny slope** instead leaves 0 dead ends.

### Step 5.4 — Erosion

Erosion exponents come from `{0.5, 1, 1.5, 2}` only — each is a product of
`sqrt` and multiply, so the arithmetic stays inside the operations IEEE 754 pins
([doc 23](../docs/23-determinism.md)).

Routing is not the hair trigger it looks like: one ULP reroutes 0 of 40,962
cells, and nothing moves until `1e-3`.

### Step 5.5 — Read-only from here on

The coarse map states where water flows across the **generated** world. Nothing
at run time rewrites it ([doc 24](../docs/24-edits-and-global-processes.md)).
With no player edits in v0.1.0 this costs nothing, and it keeps the map a pure
function of the seed.

**Done when** a seed produces continents with rivers that reach the sea, and the
same seed reproduces the same map on a second run.

## Project 6 — Terrain: height, solidity, water and material

### Step 6.1 — The height field

Sampled in **3D world space** from the cell's direction, never from face-local
`(i, j)` (invariant 4). The coarse map from Project 5 supplies the continent and
river terms; noise supplies the detail.

### Step 6.2 — Solidity

`solid(cell)` compares the cell's layer against the height at its direction. One
height-field evaluation, no storage.

### Step 6.3 — Water placement

Water is a **block type**: translucent, no collision, written by the generator,
never simulated ([doc 25](../docs/25-water.md)). There is no fluid system, no
flow, no level-seeking and no water surface primitive.

The rule is one line: below the water surface and above the ground, place water.
Sea level is a radius; river surfaces come from Project 5.

On the worked planet that gives 69.2% of columns holding water and 1,589,689
water cells.

### Step 6.4 — The density term

Caves. Gated behind a measurement: it costs **51×** the height term over a full
crust (`volume.js`), and it only carves enclosed voids when its noise gradient
exceeds 1. Build it, measure it, and keep it only if Project 16's budget holds.

**Crust depth and the density term are the same experiment.** With the height
field alone, solidity is `layer > heightLayer` and a chunk costs **561**
evaluations however deep the crust runs. The density term needs 3D noise per
cell per layer, so the same chunk costs **244,035**. A 435-layer crust adds
nothing to the height field, and is the whole bill once caves are switched on.

Measured on one 561-column chunk over 435 layers: **3.8 ms** for the height
field and **56.2 ms** with the density term, **15x**. Caves are off by default
and stay off until Project 16 has a frame budget to spend them against.

### Step 6.5 — Material and color

One flat color per cell from material band, height and slope. Deterministic,
integer-seeded, no texture sampling.

## Project 7 — Chunks and residency

### Step 7.1 — Chunk identity

A chunk is one triangle at `chunkLevel` 6. It holds a uniform **561** slots and
addresses them as `index = rank(q,r) × layerCount + layer`. The 8.7% of slots a
chunk does not own is the price of that uniform stride, and it is paid
deliberately (`rank.js`).

At 435 layers that is **244,035** cells a chunk, against 35,904 at the 64 layers
the design assumes. Crust depth multiplies chunk memory linearly, which is what
makes it a useful axis to push in a performance test.

### Step 7.2 — Chunk generation

`(seed, chunkId, level)` to typed arrays. Typed arrays throughout, never an
array of objects — measured at **15×**, larger than any language gap in the
study ([doc 28](../docs/28-language-and-runtime.md) §5).

### Step 7.3 — The worker pool

Generation runs off the main thread. `hardwareConcurrency − 1` workers, results
returned as transferable typed arrays. The coarse map from Project 5 is shared
into each worker rather than recomputed.

The pool is handed a factory rather than constructing workers itself, because
how a worker script is located belongs to the build. `ChunkWorkerCore` mentions
neither `Worker` nor `postMessage` and runs under plain Node, so the browser
file is the message plumbing and holds no logic.

The coarse map crosses as five typed arrays. `CoarseMap` holds an index rather
than a grid for this: the ring of neighbours and the direction per cell are
31 MB that only the build reads, and cloning them into every worker would copy
them once per core. One chunk generates in **5.9 ms** at depth 11.

### Step 7.4 — Residency

Which chunks are needed, given camera position and altitude. A chunk is in range
when the viewer's direction is within the horizon plus the chunk's own angular
size — one dot product per chunk, the same test interest management runs per
player. Nearest first, so a caller that stops early holds the ground underfoot.
LRU eviction under a stated memory budget.

**Altitude is what breaks it, and LOD is the answer rather than an
optimisation.** A chunk is 478 KB and the planet carries 81,920 of them, so
selecting by horizon alone gives:

| Viewer | Chunks | At full crust depth |
|---|---|---|
| eye height, 1.7 m | 59 | 28 MB |
| 100 m up | 2,448 | 1,142 MB |
| 1 km up | 15,534 | 7,247 MB |
| orbit, 4R | 31,184 | 14,548 MB |

Walking is comfortable and everything above it is not. A viewer in the air
needs distant chunks at a coarser level and a shallower crust, which is
Project 10. Until then residency takes a limit and the caller sets it from the
memory budget: a 256 MB store holds 548 chunks.

## Project 8 — The mesher

`@chamfer/mesh`. No WebGPU types anywhere in this package.

### Step 8.1 — Surface extraction

A face is emitted where a cell is more opaque than what is next to it, across
all six sides plus up and down. Opacity is 0 for air, 1 for water and 2 for
everything solid, and one comparison covers every case: a seabed draws a face
through the ocean, water against stone draws none, water against water draws
none.

Measured over the 59 chunks under a standing player: **991,925 water cells give
30,349 faces, 3.06% of them.**

**The cost model in `mesh.js` counts a surface with shared vertices and no
color.** Per-cell color and per-vertex occlusion both forbid sharing, so a cap
is 6 vertices rather than an amortised 2. Real terrain measures **9.04 triangles
and 14.08 vertices a cell**, against 4 and 2 for the bare surface: the rest is
side walls, which gentle ground still produces two or three of a cell.

### Step 8.2 — Geometry

- Corners from Step 2.5: average the flat lattice points, then project.
- Chunk-relative `float32`, which gives 122 µm at radius 1,700 m
  (`precision.js`).
- Up-triangles and down-triangles need **different emit patterns**. Listing a
  downward triangle by the same rising-index rule as an upward one winds it
  inward and holes the mesh (`winding.js`).
- A pentagon has 5 corners and 3 triangles.

### Step 8.3 — Vertical run-length merging

Exact, and it follows from invariant 10: the tessellation is identical at every
layer, so a column is straight. The rectangle-growing half of greedy meshing has
no hexagonal equivalent and is not attempted.

**It collapses nothing on this terrain, and that is a property of the terrain
rather than of the merge.** A 20-layer wall does come out as one quad, which a
test pins exactly. Real ground at 1 m cells steps by about one layer between
neighbours, so every exposed run is one block tall and there is nothing to
merge. Cliffs and player edits are what it is for.

The sea surface merging **37 cells into one quad** is the rectangle-growing
half, and is not attempted for the same reason.

### Step 8.3b — Bounding the scan

A column carries the band anything can happen in: the first layer that is not
air and the last that is not solid. A cell takes the widest band over itself and
its six neighbours, and no face exists outside it.

Walking all 435 layers instead costs **80.2 ms a chunk**; the band costs
**15.8 ms** for the same output. On this terrain the band is a few layers on
land and about eighty at sea. Both numbers are properties of the column rather
than assumptions about the terrain, so a cave lengthens the scan instead of
being missed.

**The crust floor is left out**, behind an option. It sits 435 layers down under
solid ground, no camera can be beneath it while the world has no digging in it,
and it was **34.6%** of every chunk's triangles.

### Step 8.4 — Two buffers per chunk

Opaque and translucent geometry go into separate buffers, because Project 9
draws them in separate passes.

### Step 8.5 — The sink

`mesh` declares the interface it writes through. `render` implements it. This is
what keeps the mesher testable under plain Node.

### Step 8.6 — Ambient occlusion

Per-vertex, from the cells touching each corner. A hexagon corner is shared by
three cells rather than a cube's four, so a vertex has **two** other cells
touching it and the shade takes **three** values. Cube-world tables have four
and do not carry over.

## Project 9 — Translucency and the water pass

Proven in outline by Step 3.4; here it meets real geometry.

### Step 9.1 — Two passes

Opaque first, then water back to front. Depth test on for both, depth write off
for the translucent pass.

### Step 9.2 — The sort is of one thing

A view crosses **one** water surface 82.3% of the time and two 0.6%, worst case
3, because water fills a column from the floor up. Sorting is per chunk, not per
triangle: the surfaces do not interpenetrate.

Generated water has **zero exposed vertical sides** — it is always held in by
land at or above its own level.

### Step 9.3 — Underwater

The camera inside a water cell needs a tint and the far plane pulled in. This is
a cell test on the camera position, which is Project 2's lookup:
`blockAtPosition` is position to cell and a block read, the same query floating
in water is. There is no water volume to test against.

### Step 9.4 — On screen

The client draws terrain. The camera looks at a point on the surface from a
little behind and above it; dragging moves the point across the planet and
scrolling changes the height.

**The opening view is found from the coarse map alone** — three array reads a
chunk rather than a noise evaluation, which is 27 ms over 20,993 chunks instead
of a second, and it lands on ground 33 m above sea level rather than on the
first dry cell it meets.

**Altitude is capped at 10 m, and the number is measured rather than chosen.**
The horizon grows fast, and a chunk takes 14 ms to build:

| Camera | Horizon | Chunks |
|---|---|---|
| eye height, 1.7 m | 76 m | 72 |
| 8 m | 165 m | 260 |
| 12 m | 201 m | 377 |
| 40 m | 365 m | 1,127 |
| 80 m | 512 m | 2,120 |

The ceiling is where the horizon still fits in the budget, so the view ends at
the real horizon rather than at a hard edge. Height beyond it needs distant
chunks at a coarser level, which is Project 10.

Chunks are built one per frame, so the page keeps drawing while it fills.
Generation is on the main thread here: the worker pool returns blocks and
meshing would still land on the main thread, so moving both into the worker is
one change and it belongs with Project 16.

**Done when** an ocean, a lake and a river all read correctly from above the
surface, at the shore, and from underneath.

## Project 10 — LOD and seams

This is what makes the space view possible, and it is the hardest project here.

### Step 10.1 — Level selection

LOD is **resampling, not decimation**. Goldberg levels do not nest, so a coarse
chunk re-evaluates the terrain function at a coarser spacing rather than dropping
cells ([doc 14](../docs/14-meshing-and-lod.md)).

**Subdivision depth and chunk level drop together.** A chunk one level coarser
covers four times the area at half the resolution, so it holds the same 561
slots and costs the same to build, and there are four times fewer of them.
Holding the chunk level fixed instead puts **81,920** chunks on a planet that is
**40,962** cells at its coarsest level — more draw calls than cells.

Selection walks the triangle hierarchy down from the twenty faces, which is what
that hierarchy is for. A triangle more than `DETAIL` times its own width away is
drawn; a nearer one splits into its four children and each is asked again.
Children tile their parent exactly, so the surface is covered once with no gap
and no overlap however the levels fall — a test samples directions inside the
horizon and requires exactly one chunk to hold each.

`DETAIL` is 2, chosen from the worst altitude rather than picked. Near and far
chunks are both in view around 60 m up, which gives **321** chunks at 2, 471 at
2.5 and 633 at 3.

| Camera | Chunks | Levels in view |
|---|---|---|
| 2 m | 62 | 0 |
| 10 m | 281 | 0 |
| 60 m | 633 | 0, 1, 2 |
| 300 m | 464 | 1, 2, 3 |
| 2 km | 111 | 4, 5 |
| 5.1 km | 37 | 5, 6 |

### Step 10.2 — Far chunks run the height field alone

The density term is dropped beyond a threshold. A coarse mesh cannot represent a
cave anyway — a 3 m cave is gone by level 10.

### Step 10.3 — Seams

**Layer boundaries agree across levels**, because the crust top does not move
and layers double with cells: layer `L` at one level is layer `L · 2^lod` at the
finest. So a seam between two levels can only open horizontally.

How far it opens is measured. Over 40,000 directions, neighbouring levels put
the ground at:

| Levels | Mean gap | Worst | As cells of the finer level |
|---|---|---|---|
| 0 → 1 | 0.12 m | 0.73 m | 0.73 |
| 1 → 2 | 0.23 m | 1.54 m | 0.77 |
| 2 → 3 | 0.44 m | 3.15 m | 0.79 |
| 3 → 4 | 0.81 m | 5.38 m | 0.67 |
| 4 → 5 | 1.47 m | 10.36 m | 0.65 |
| 5 → 6 | 2.46 m | 18.06 m | 0.56 |

**Under one cell of the finer level at every level**, so a skirt two cells deep
covers every seam with margin. The skirt hangs from the chunk's rim and costs
the rim rather than the area: doubling a chunk's side quadruples its cells and
near-doubles its skirt.

**Seam ownership is what the density term needs, and the density term is off.**
A skirt closes a surface slit and `seam.js` measures it closing about 1% of cave
mouths, because a skirt hangs downward and a cave mouth is a horizontal hole.
With one run of ground a column there is no such hole, so the skirt is the whole
of it. Turning caves on brings back the 961 holes a skirt alone leaves, and the
finer chunk has to emit a face wherever its solidity differs from the coarse
neighbour's.

### Step 10.4 — The space view

Measured from three planet radii out: **55 chunks, 219,324 triangles, 10.4 MB
of buffers, 376 ms to build the lot.** Against 41,943,042 cells at level 11.

The camera runs from 2 m to three radii, and the near plane opens with altitude
so the depth buffer keeps its range.

**A coarser grid than the coarse map is a case, and it was wrong.** Sampling the
map at a depth below its own level computed a negative shift, and the levels
disagreed by 83.65 m at the seam instead of following the trend. Lattices at
different depths nest exactly — `(i, j)` at one depth is `(2i, 2j)` at the next
— so a coarse grid names the cell rather than interpolating. The gap fell to
10.36 m, in line with every other level.

**Done when** the transition from eye height to orbit and back holds frame rate
with no visible holes at any seam.

## Project 11 — Lighting and ambient occlusion

Light is a scalar, so holonomy and the pentagon direction deficit do not apply to
it at all ([doc 16](../docs/16-lighting.md)).

### Step 11.1 — Sky light

Radial, down a column, monotone. Invariant 10 makes a column straight, so this is
as cheap as it is in a flat world. Stored **per column**.

**The saving is the crust depth, and 32× is what a 32-layer crust gives.** At the
435 layers this world runs, a chunk holds 561 sky values against 244,035 cells:
**435× smaller**.

**Nothing is stored at all here.** With the height field alone a column is one
run of ground, so the layer sky light reaches is the layer the ground starts at,
which the chunk already carries. A stored light field arrives with the density
term, which is what puts air under rock.

What the ground does need is **how much sky a cell can see**, from the ground
standing around it. A hollow is darker than a ridge, and the occlusion at a
face's corners cannot see that: it only ever looks at the two cells touching the
corner. Both are baked into the vertex color by the mesher, which already has
the ring resolved.

### Step 11.2 — Sun and terminator

One dot product against gravity's `up`, and that is the whole of day and night:
every point carries the answer in its own position, so there is no terminator to
track and nothing to store. Measured at `1.40 m/s` for a 2.12 hour day, which is
walking pace — a player outwalks the sun below that and can hold a sunset in
place by walking west. The client runs a 240 second day, where it moves at
`44.5 m/s`.

The sun keeps a fixed angle to the polar axis. **At zero every place off the
axis gets a full day and night, and the two poles sit on the line between them
and stay there** — both poles are pentagons, and both are the coordinate poles.
Leaning it puts one pole in daylight all day and the other in the dark, which is
what a fixed lean does with no year to turn it round.

### Step 11.4 — What a hex grid costs to light

Walked over the engine's own adjacency rather than taken from the formula:

| Range | Hexagons | Squares | Ratio | Pentagon | Share |
|---|---|---|---|---|---|
| 4 | 61 | 41 | 1.488 | 51 | 0.836 |
| 8 | 217 | 145 | 1.497 | 181 | 0.834 |
| 15 | 721 | 481 | 1.499 | 601 | 0.834 |

`3r² + 3r + 1` against a square grid's `2r² + 2r + 1`, tending to **1.5×**. A
pentagon reaches `1 + 5r(r+1)/2`, **five sixths** of a hexagon's: a ring there
holds `5k` cells where a hexagon's holds `6k`, so a torch at a pentagon is not
dimmer, there is less world within reach of it.

A disc has to clear the twelve pentagons for the hexagon count to hold, which is
what the test walks out to find.

### Step 11.3 — Shading

Flat cell color times light times ambient occlusion. No textures in v0.1.0.

The mesher bakes the block's color, the face's direction, its corner occlusion
and the cell's sky exposure into one vertex color. Over 131,166 vertices of a
real view that spreads a shade from `0.297` to `0.742`. The sun is the one term
left to the shader, because it turns.

**Light storage is nothing in v0.1.0.** Doc 16 budgets 4× the block data, halved
by the per-column rule; with no density term there is no stored light field to
budget for, and Project 7's residency numbers stand as measured.

## Project 12 — Sky, atmosphere and clouds

All presentation, so this is where the transcendentals
[doc 23](../docs/23-determinism.md) keeps out of the generator are spent
([doc 32](../docs/32-sky-clouds-and-moon.md)).

### Step 12.1 — The skybox is world-fixed

Walking turns your own `up` by `s/R` — 3.37° per 100 m, and a full 360° over the
10,681 m circumference. A view-fixed skybox makes the stars follow the player
around the planet.

### Step 12.2 — Atmospheric scattering

Correctly scaled air gives a zenith optical depth of `7.4e-5` against Earth's
`0.277` — **3,748× too thin**, and a black daytime sky. Angles scale and path
lengths do not.

The ratio is the two radii and nothing else, so **no choice of air fixes it**: a
test runs it at each of the three Rayleigh coefficients and gets the same
number. Earth-like needs air 3,748× denser, or an atmosphere **4.7×** the
planet's radius.

Scaled air is thin sideways as well. A grazing path through it is **85 m**,
against **319 km** on Earth, and the ground a standing player can see reaches
**76 m** — so a scaled sunset has neither the air nor the geometry for a horizon
glow.

So the scattering runs on a **fictional Earth-sized atmosphere**: single-scatter
Rayleigh and Mie marched against Earth's radius and scale heights, with the
camera's real height lifted onto Earth's by one factor. **Only the sun's
direction comes from the world.**

### Step 12.3 — Clouds

Clouds borrow the lattice and are **not cells**. A cloud has no cell ID, no
chunk, and no layer — `layer` counts downward from the crust top, so there is no
value it could take.

A cloud is a lattice point indexed by `(face, i, j)` into a transient buffer, the
way a vertex is rather than the way a block is. Level 5 gives **10,242 points**
for the whole sky against 41,943,042 cells in one surface layer, **40 KB** of
cover, built in 19 ms. Under 9% are in view at 300 m up.

The buffer is thrown away and refilled as the wind turns, because there is no
address to update in place. That is the point of withholding one: everything
that stores a thing here is keyed by cell ID, so a cloud with no ID cannot be
stored even by accident.

The hexagons come from `cellCorners` at a larger radius. The construction that
puts cells on a sphere never mentions a radius, so the same lattice is there at
any height.

### Step 12.4 — Wind

**One axis and one rate**, rotating the sample point before the noise lookup. The
hairy ball theorem forbids a uniform wind. Of the two obvious fields only rigid
rotation is divergence-free — measured mean `|div|` of `4.7e-12` against `0.9983`
for a projected world vector, over 20,000 points. Calm patches are **0.35%** of
the surface under 1 m/s, at the two points the axis comes out.

### Step 12.5 — The moon

Angular size is an art decision; a faithfully scaled real moon is still **0.518°**,
because scaling preserves angles. Its **distance** is not an art decision:
walking round the planet shifts it **1.90°** against the stars, so it cannot be
painted into the skybox. It is placed at a distance and the direction to it is
computed from the camera, which is what gives it that shift.

**Demo:** [`demos/sky-on-a-small-planet.html`](../demos/sky-on-a-small-planet.html)
shows all of this moving.

## Project 13 — Player, movement and frames

### Step 13.1 — The three frames

Axis for coordinates, transported for the camera, grid for machinery. They are
three frames for three jobs and must not be interconverted casually
([doc 13](../docs/13-gravity-and-orientation.md)).

**The player carries the transported one.** A heading is a direction along the
ground, so it only means anything against the ground it is standing on: moving
somewhere else takes the part of it that is still sideways and makes it a unit
vector again. Nothing is measured against a fixed direction, because there is no
fixed direction to measure against.

**A heading carried around a closed loop does not come back where it started.**
Walked rather than asserted: a right-angled triangle over an eighth of the
sphere, carrying the heading the whole way, and it comes back turned by `pi/2` —
the area enclosed over the radius squared. That is not a defect to correct. It
is why nothing here accumulates an angle.

### Step 13.2 — Gravity

`up` is `normalize(position)`. There is no global up and no global north — the
hairy ball theorem forbids one, so a heading is never stored as a world vector
(invariant 8).

`float32` holds `up` to 0.005″ at every radius, so directions need no precision
handling even where positions do.

### Step 13.3 — Floating origin

Anchor plus offset, offset in `float64`, which gives `7.1e-15 m` over a 32 m
chunk. Never cache a world-space position across a frame — recompute it
(invariant 13, [doc 15](../docs/15-precision-and-origin.md)).

### Step 13.4 — Walking

1.4 m/s. The ground test samples the cell the player occupies and the one below,
which is Project 2's position lookup plus a solidity read. Step up one block.

A falling player crosses 1.67 m per frame at 30 Hz, so the fall is tested
against every layer it crosses rather than against the endpoint. That is a walk
down one column, which invariant 10 makes straight.

### Step 13.5 — Swimming

Water does not collide, and floating is a different question from collision:
collision is a **face** test, floating is a **cell** test — the position lookup
plus a block-type read.

A falling player goes **through** the surface rather than landing on it, and
then floats rather than sinking to the bed. Those are the two tests answered
separately, and a test drops a player from 60 m into 40 m of water to see both.

At 1 m blocks a 1.8 m player stands in one block of water and swims in two, so
walking and swimming are separated by a **threshold one cell wide**. There is no
partial-buoyancy case to write.

The generated world makes this playable without designing for it: 85.3% of the
water's edge is one block deep, a player can step out at 99.9% of shore columns,
and all 58 bodies of water have an exit.

### Step 13.6 — Flying

Higher speed, no collision, speed scaling with altitude so orbit is reachable in
reasonable time.

### Step 13.7 — Space mode

Pull back to orbit and look down. Interacts directly with Project 10 — the
transition is where LOD selection is under most pressure.

## Project 16 — Performance

The point of the release.

### Step 16.1 — Instrumentation

Frame time against a 16.6 ms budget at 60 Hz, split by phase: generation,
meshing, upload, draw. GPU timestamp queries where the adapter exposes them.

World creation is measured separately. Nobody has timed the coarse map, and a
client regenerates it on load rather than downloading it — if it is slow it needs
a loading screen ([doc 29](../docs/29-what-runs-where.md)).

### Step 16.2 — Reference scenes

| Scene | What it tests | Expected load |
|---|---|---|
| Eye height, flat ground | the floor case | ~21,000 cells, 84k triangles |
| Eye height, 120 m relief | real terrain | 9.5 triangles per cell |
| Standing at the shore | the translucent pass | one surface, sorted per chunk |
| Underwater | the camera inside a water cell | tint, near geometry |
| Standing on a pentagon | the degree-5 path | one cell, every frame |
| Orbit | LOD at its coarsest | whole planet, level 5–7 |
| Terminator crossing | lighting under change | full sky light re-evaluation |
| Flying at speed | residency churn | chunk load and evict under pressure |

The 21,000 figure is a **floor**, not an estimate — it assumes flat ground, and a
60 m hill raises the visible count 47× (`volume.js`).

### Step 16.3 — Feed the results back

Every measurement that contradicts a number in `docs/` gets the document
corrected, with the script updated to match. The specification is the shared
base; where the engine proves it wrong, the engine wins and the document moves.

`volume.js`, `mesh.js` and `seam.js` were on the float-multiply hash and the
smoothstep fade, so they measured a planet the generator does not produce. All
three now run `noise.js`'s pinned hash and quintic fade. What moved:

| Figure | Was | Is |
|---|---|---|
| Holes at a LOD seam, no skirt | 1,041 | **1,150** |
| Holes with a skirt one coarse cell deep | 961 | **1,060** |
| Holes with the finer chunk owning the seam | 0 | **0** |
| Faces per rim column the seam rule costs | 2.70 | **2.99** |
| Multi-span columns under a density field | 8–24% | **13–32%** |
| Deepest cave mouth below the surface | 15 layers | **18 layers** |
| LOD seam gap at level 11 | 0.263 m | **0.300 m** |
| Triangles per column at 120 m of relief | 9.48 | **9.53** |

Every conclusion held. They are ratios over hundreds of thousands of cells, and
none of them turned on which world it measured.

Two scripts were quoting a wall-clock timing as a headline, which made the
corpus disagree with itself every time `npm run reference` ran on a different
machine. `language.js` divided a live JavaScript mesher timing by a stored Rust
one — a ratio that measures the machine, not the language — and `authority.js`
built its CPU-per-player table from a live query cost. Both now quote the
recorded figure and print this machine's beside it, marked as a timing.

**Nothing else in `docs/` was contradicted.** Three engine figures look like
they disagree with a document and do not, because they answer a different
question, and the difference is worth writing down rather than reconciling:

- `mesh.js` says a standing player sees **21,000 cells**. That is the disc
  inside a 76 m horizon. The engine *holds* 100,353 cells at eye height,
  because residency is not bounded by the horizon — a hill beyond it is
  visible, which the same document says.
- Doc 14 costs an unmerged hex surface at **2 vertices, 4 triangles** a cell.
  That is a shared-vertex top surface. A chunk emits caps, sides and
  skirts, and shares no vertex at all, because color is per cell and occlusion
  is per vertex per face: **7.29 triangles and 11.60 vertices a cell** on low
  ground.
- `volume.js` prices the density term at **51× the height field** in noise
  evaluations. The engine measures **17.3×** in milliseconds over a whole
  chunk build, because the height path does not evaluate the deep rock at all —
  it is one fill.

### What Project 16 measured

Run it with `npm run bench`. The reference scenes, at radius 1,700 m, depth 11,
chunk level 6, a 1.0000 m block and a 435-layer crust:

| Scene | Chunks held | Drawn | Cells | Triangles a frame | Build |
|---|---|---|---|---|---|
| Eye height, flat ground | 196 | 74 | 100,353 | 307,190 | 2,649 ms |
| Eye height, relief | 323 | 115 | 165,553 | 332,728 | 2,988 ms |
| Standing at the shore | 88 | 38 | 45,086 | 172,310 | 1,211 ms |
| Under water | 2 | 2 | 1,025 | 7,716 | 24 ms |
| Standing on a pentagon | 60 | 28 | 30,720 | 89,592 | 701 ms |
| Sixty metres up | 330 | 115 | 169,154 | 356,788 | 3,027 ms |
| Orbit at 3R | 28 | 28 | 14,338 | 96,584 | 194 ms |

**A chunk takes longer than a frame and always will**, so it is not built in
one: 8.5–13 ms each at the finest level, against a 16.6 ms budget. Generation
and meshing are one job on a worker, and the thread that draws only uploads what
comes back. On seven workers a whole view fills in **0.35–0.42 s**.

**Blocks never cross back from a worker.** A chunk is 478 KB of them and the
geometry is 210 KB, and the thread that draws has no use for the blocks — which
is why generating and meshing are one job rather than two.

**A frame draws the part of the held disc it is looking at**, 35–43% of it.
What is out of view stays resident: turning is instant and building is not, so
dropping it would put a hole in the world every time someone span round.

Churn, flying along the ground from 20 m up: **11 of 324 chunks are new** after
10 m, 68 after 50 m, 222 after 200 m. At 200 m that is 2.7 s of worker time on
seven workers, which is what bounds how fast the world can be crossed before the
edge of it stops keeping up.

World creation is **1.0 s** for the coarse map at level 7, on the thread that
draws, behind a loading line.

Three changes made the build cheap enough to fit on a worker at all:

- **The band comes from generation, not from a scan.** Every column's first
  non-air and last non-solid layer is written as the column is written. Reading
  them off afterwards meant walking the whole 435-layer crust of 658 columns to
  find a handful of layers, and it was 14% of the whole run.
- **The deep rock is one fill.** Below the soil every layer is stone to the
  crust floor, so a column evaluates about 10 layers and fills 425.
- **`cellCorners` allocates nothing per corner.** It was six `Float64Array`s a
  cell; the ring and the running total are now refilled. 5,815 ns to 2,138 ns.

Together they took a chunk from 27.9 ms to 16.2 ms, before it moved off the
thread that draws.

**What is measured here is the half of a frame that runs on a CPU.** The draw
needs an adapter. The client reports its own frame time, worst frame, and phase
split on the budget line, and asks the adapter to time the pass where
`timestamp-query` exists.

## Open questions

- ~~The density term.~~ **Dropped**, on Project 16's numbers. At the worked
  planet's crust it costs **261.9 ms a chunk against 15.2 ms** — 17.3× — and
  emits **75,603 triangles against 4,303**, 17.6×. It is not a margin a
  shallower crust rescues: at 256 layers it is still 99.2 ms and still 7×. The
  code is written and off behind `TerrainOptions.caves`, so turning it on is one
  flag when there is a budget to spend on it.
- ~~Whether 435 layers survives Project 16.~~ **It survives, and the ordering
  never had to be exercised.** With the height field alone the crust is
  nearly free — 15.2 ms at 435 layers against 14.0 ms at 256 — because the deep
  rock is one fill rather than 400 evaluations. It costs memory linearly, 479 KB
  against 283 KB, and that memory is a worker's and never crosses to the thread
  that draws. The crust also has a floor it cannot go below: it has to reach
  from the top of the tallest ground to under the deepest sea, which is 229
  layers before anyone digs.
- **Coarse map level.** [Doc 21](../docs/21-rivers-and-erosion.md) prices it at
  level 8 and 2.5 MB. Whether that resolution gives rivers that read well at
  1 m cells is unmeasured.
